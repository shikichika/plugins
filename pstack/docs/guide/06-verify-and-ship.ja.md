# 結果を検証し、PR を開く

「コンパイルは通った」は証拠ではありません。[Prove It Works 原則](../../skills/principle-prove-it-works/SKILL.md) は、エージェントに成功を報告する前に実アーティファクトをチェックさせ、あなたの仕事はその「実アーティファクト」をチェック可能にすることです。このページでは、完了条件の明示、測定した数値の検査、アプリ用検証スキルの生成、テストが届きにくい性質の形式的検証、PR のオープン、マージ可能状態までの運転を扱います。

検証はたいていのエージェント作業で最も遅いステップです。人間を待つことが多いステップだからです。エージェントがそれをできるようにすれば、あなたはボトルネックではなくなります。飛ばせば、エージェントを増やしてもレビュー待ちの未チェック作業が増えるだけです。

![プロトタイプの飛行機が本物のテストコースを飛び、彼女はストップウォッチで計時し、ロボットが走行を撮影しチェックリストにチェックしている。ターミナルには verify: pass, evidence: captured とある。](./images/verification.jpg)

## 完了条件を最初に述べる

完了の意味を、最初のプロンプトに、合う言葉で入れてください。

```text
/poteto-mode add json output to this command. text output stays byte-identical, the json parses, both run against the sample project. show me the evidence.
```

これでエージェントは、満たすべき気分ではなく、実行できる 3 つのチェックを持ちます。返答が戻ってきたら、正確なコマンドと出力を伴うはずです。チェックが実行できなかった場合、良い返答は「inconclusive」と言います。証拠のない自信ある返答は警戒信号です。

変更にチェックを合わせてください。

- CLI の変更は実際のコマンドを実行します。
- UI の変更は実行中のアプリで変更されたフローを歩きます。ピクセル単位でリファレンスに一致しなければならない場合、[Visual parity プレイブック](../../skills/poteto-mode/playbooks/visual-parity.md) が目で判定する代わりに凍結したベースラインに対してスクリーンショットを差分します。
- パーサやマイグレーションは保存された入力をリプレイします。
- パフォーマンスの変更はビフォーアフターのプロファイルを比較します。
- ストレージの変更は書き込まれた値を読み返します。

あなた自身が検査できるアーティファクトとして証拠を要求してください。失敗するテストとそのあとパスするテスト、ビフォーアフターの動画、トレース、スクリーンショットです。修正がすでにマージされているなら、main 上で同じチェックをもう一度要求してください。もっともらしい説明より、アーティファクトの方が優れています。実行全体をリプレイせずに挑戦できるからです。

あまり信用しきれない小さな差分には、[`/blast-radius`](../../skills/blast-radius/SKILL.md) が他で何を壊しうるかを見つけます。変更を安全にする 1 つの事実を見つけ、議論ではなくコードを動かすことでその事実を証明します。

## `/benchmark-checklist` で測定値を検査する

ビフォーアフターの数値は、うっかり間違えやすい証拠の筆頭です。温まったキャッシュ、片側だけデバッグビルド、計測区間外で行われた作業は、どれも説得力のある高速化を生みます。数値を報告したり数値に基づいて行動したりする前に打ってください。

```text
/benchmark-checklist vet the export speedup before it goes in the pr
```

[`/benchmark-checklist`](../../skills/benchmark-checklist/SKILL.md) は 7 つの質問をし、それぞれに実行からの証拠を求めます。

1. 何がこの数値を制限しているか、そして 2 倍でない理由は何か。
2. すべての側がプロダクションと同じようにチューニングされて走ったか。
3. ディスク帯域やコア数など、物理限界を破る結果になっていないか。
4. 何かがエラーになったり、間違った出力を返したりしなかったか。
5. 中央値と範囲を伴って、交互実行で再現するか。
6. ユーザーが待つパス上で、エンドツーエンドに意味があるか。
7. 作業は本当に計測区間の中で行われたか。

判定は、より速い、より遅い、有意差なし、不確定のいずれかで、実行回数、範囲、制限要因とともに返ります。制限要因を命名できないか、片側が未チューニングで走ったときは inconclusive と言います。`/poteto-mode` はすでに Perf issue と Hillclimb プレイブックの中でチェックリストを実行するので、自分で打つのは、それらの外で何かを測ったときや、誰かの数値が良すぎるときです。これは [Explain the Number 原則](../../skills/principle-explain-the-number/SKILL.md) の実践形です。

## プロジェクト検証スキルを作る

上の UI の箇条書きは本物の要件を隠しています。エージェントはあなたのアプリをスクリプトで動かす方法を必要とします。プロジェクトにそれがあればよし。なければ実行してください。

```text
/create-verification-skill
```

[`/create-verification-skill`](../../skills/create-verification-skill/SKILL.md) はあなたではなくリポジトリをインタビューします。ユーザーが何に触れるか、アプリがローカルでどう起動するか、何がそれを動かせるか（既存のハーネスが第一、なければブラウザと CDP、PTY、プレーン HTTP）、何が挙動を証明する証拠か、2 つのインスタンスを並列で走らせられるかを突き止めます。コードが答えられないことだけをあなたに尋ねます。

書き込み先は `.cursor/skills/verify-<app>/` です。これはエージェント向けの指示で、正確な Launch、Doctor、Drive、Evidence、Cleanup のセクション、同梱スクリプト用の Helpers セクション、そしてアプリが何をするかと各機能の正常を証明する結果を索引する `features/` 以下の feature map を含みます。スキルは `features/` に [実例の feature map](../../skills/create-verification-skill/references/feature-map-example/) を同梱し、README インデックスと 4 つの必須 H2 を使う機能ごとのファイルを提供します。引き渡す前に、生成器はスキルをエンドツーエンドで 1 度証明します。起動、doctor チェック、1 機能の駆動、証拠のキャプチャ、クリーンアップを行い、クリーンアップ後も証拠が残っていることを確認します。その証明が失敗したら、出力を使わないでください。

これ以降「アプリ内で検証する」は、このリポジトリでは任意のエージェントが実行できるステップになり、セットアップの会話は要りません。特定の形式で証拠が欲しいときは、プロンプトでそれを指名してください。

```text
/poteto-mode build the bulk-archive action. use /verify-<app> to verify your changes and show me a video and screenshots as proof.
```

```text
/poteto-mode repro this with /verify-<app>. if it repros on main, fix it and show me a video as proof.
```

verify スキルが動けば、[`/swarm`](../../skills/swarm/SKILL.md) は feature map のエントリで完全パスを分割して結果を集約できます。verifier の swarm は十分なサンプルサイズでのパフォーマンス勝利の確認や、PR 出荷前のリグレッションのファジングにも使えます。

検証スキルは使い捨てではなくインフラとして扱ってください。コミットすれば、チームの全員と全エージェントが同じ方法でアプリを動かします。そこで [てこを作ってください](../../skills/principle-build-the-lever/SKILL.md)。エージェントがアプリをクリックして回る使い捨てスクリプトを書き続けるなら、スキルが呼び出す小さなコントロール CLI を求めてください。エージェントはより少ないトークンを使い、各実行は再現可能になります。エージェントがうまく使う CLI には次の特徴があります。

- 薄いコマンドを多数ではなく、本当の作業をする構成可能な少数のコマンド。
- 破壊的なものに対する `--dry-run` オプション。
- すべてを一度にではなく、徐々に機能を明らかにするサブコマンド。
- 代わりに何をすべきかを伝えるエラーメッセージ。
- 充実した `--help` テキスト。
- JSON などの機械可読出力。

ついでに、開発セットアップも再現可能にしてください。シードデータ、テストユーザー、毎回同じ方法で環境を立ち上げる単一のコマンドです。

## 検証スキルを正直に保つ

アプリは変わり、feature map は古くなります。少なくとも 1 日 1 回、理想的には誰も覚えておかなくてよいようスケジュール自動化から実行してください。

```text
/maintain-verification-skill
```

[`/maintain-verification-skill`](../../skills/maintain-verification-skill/SKILL.md) は生成されたスキルを監査します。機能ごとに 1 つの読み取り専用ソースリーダーを並列に、次にマップされた全機能を駆動するライブパスを 1 回実行します。終了は正確に 3 つの結果のいずれかです。`clean` は完全カバレッジで出荷するものがないことを意味します。`changed` は検証スキル自身のディレクトリ内に限定された、証明済みの修正の PR 1 つを意味します。`blocked` はブロッカーを命名します。プロダクトコードは決して編集しません。ライブパスがプロダクトリグレッションを捕まえたら、ドキュメント編集で隠さず、リグレッションを報告します。

## 形式検証スキルで性質を証明する

検証スキルはあなたが駆動するパスを証明します。一部のバグは誰も駆動しないパスに住んでいます。2 つのリトライが重なる、書き込み中にロックが切れる、順序が入れ替わって到着する状態変化などです。テストはそれらのケースに届きにくいものです。そんなバグが高くつくコードには実行してください。

```text
/create-formal-verification-skill
```

[`/create-formal-verification-skill`](../../skills/create-formal-verification-skill/SKILL.md) はコードからターゲットを選びます。コードがする約束で、破るとユーザーに害があり、テストが壊れるケースに届きにくいものです。検証しやすさではなく、最も強いターゲットを選びます。特定の領域やバグから始めるなら、それを命名してください。

```text
/create-formal-verification-skill the job lease and retry logic. a job must never run twice at once.
```

質問が道具を選びます。イベントが悪い順序で起こりうるかは設計の小モデルに対するモデル検査に向き、任意の言語で TLA+ がそのためのデフォルトです。コードが任意の入力に対して振る舞うかは、コードを走らせる verifier に向きます。あなたの言語で動く verifier がないなら、エージェントはそう言い、関数の手書きモデルではなく実コードを生成入力でテストします。任意のサイズで成立しなければならない性質は証明が必要になることがあります。エージェントはどのツールをなぜ選んだか伝えます。

1 つの性質を検証し、その性質が壊れたコードの変異体で失敗することを示します。見たことのないチェックは何も証明しないからです。現在のコードがすでにその性質を破っているなら、あなたのコードの用語で短いステップの系列として反例が得られます。性質は述べられたまま保たれるので、発見は発見のまま残ります。あなたが頼まない限りプロダクトコードは変わりません。

書き込まれるプロジェクトローカルなスキルは、次のエージェントに対して、変更が検証されたコードに触れるかどうか、1 つのコマンドでチェックを実行する方法、本物のバグとモデリングエラーの見分け方を教えます。引き渡す前に、生成器は性質を破るスクラッチ変更でそのスキルを 1 度追い、チェックがそれを捕まえなければなりません。ハンドオフは、何を検証したか、どのツールと境界で、チェックが何を見つけ、何をカバーしないかを述べます。パスはシステム全体ではなく、モデルや境界をカバーします。

スキルはまた、各チェックがどのコードをカバーするか、チェックが最後に一致したコミットを記録します。スキルを飛ばしたマージやリファクタは、消えたコードの記述に対してチェックをパスし続けさせることがあります。それらの後に [`/maintain-formal-verification-skill`](../../skills/maintain-formal-verification-skill/SKILL.md) を実行してください。検証をコードから更新し、再実行し、更新された各チェックがまだ失敗しうることを示し、各失敗が検証のドリフトかコードのバグかをあなたに伝えます。

## 挙動をステートチャートで示す

モデル用語での反例はあなたを納得させます。その挙動を所有する PM やデザイナーは、彼らの用語で見る必要があります。実行してください。

```text
/statechart what the user sees when they edit a note offline
```

[`/statechart`](../../skills/statechart/SKILL.md) は TLA+ モデルから生成された、ユーザーから見えるものの Mermaid ステートチャートを描くので、絵とチェックされたモデルがドリフトしません。読み手のルール（「オフラインの間は Synced を見ない」）は不変条件になります。チャートはルールを破る各状態をマークし、レポートは読み手の言葉でそこへの最短経路を示します。引き渡し前に、エージェントは各バグ経路を実コードで再現するので、モデリングエラーがバグとして読み手に届きません。

## PR を開く

```text
/poteto-mode open the pr. small ordered commits, evidence in the description.
```

[Opening a PR プレイブック](../../skills/poteto-mode/playbooks/opening-a-pr.md) はワークツリーから作業し、作業を小さくランディング可能なコミットにリベースし、差分をきれいにし、1 分のブリーフィングをボディに書き、PR を準備完了で開きます。成長するブランチより、スタックしたフォローアップの方が優れています。

## Babysit で PR をマージ可能状態まで運転する

開いた PR はすぐにブロッカーを集め始めます。チェックが失敗し、レビュアがコメントし、trunk が動きます。その churn は [Babysit プレイブック](../../skills/poteto-mode/playbooks/babysit.md) に渡してください。

```text
/poteto-mode babysit this pr. get it green.
```

Babysit は GitHub 上では同梱の watcher、利用可能なら Origin CLI で PR を見張り、ブロッカーを順に処理します。コンフリクト、次にレビュースレッド、最後に CI です。決してリベースや force push はしません。コンフリクトや古いベースは、リベースが必要なブランチを添えてあなたに戻します。コメントのトリアージは懐疑的です。人間とボットは本物のキャッチとノイズを同じリストに提出するからです。本物の発見は修正され、ノイズは反証をスレッドに投稿して退けられます。ステータスだけが欲しいときは、小さく尋ねれば Babysit はループを始めずに答えます。

```text
/poteto-mode check on pr 123. anything outstanding?
```

Babysit はマージ可能で止まります。すべてがグリーンでも、マージは別の決定なので、決してマージしません。

## Shipping でスタックをランディングさせる

グリーンは安全と同じではありません。ランディングの準備ができたらそう言ってください。

```text
/poteto-mode land the stack.
```

[Shipping プレイブック](../../skills/poteto-mode/playbooks/shipping.md) は何かをアームする前に各 PR を独立して検証します。PR ごとに新鮮なエージェントが 1 つ、挙動をライブで証明し、変更を判定するエージェントはそれを書いたエージェントではありません。それから Shipping は底から連続した検証済み区間のみを、デフォルトでは GitHub を通して、利用可能なら Origin を通して 1 PR ずつランディングし、チェーンを破った最初の PR を報告します。未検証の PR の上にある検証済みの PR は待たされます。それをマージすると下に穴を引き込むからです。
