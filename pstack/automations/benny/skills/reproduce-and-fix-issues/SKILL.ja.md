# イシューの再現と修正

ソーススレッドで信頼済みのトリアージマーカーを待つ。ターゲットアプリの実 UI を通じて、同じ症状を正確に再現する。既存の修正があれば検証する。修正を試みるのは、再現が確認された後の範囲を限定した 1 回のみ。

オートメーションが提供する外部 Benny 設定を読み込む。設定、必要なアクション、コントロールアダプタ、完成済みフィーチャーマップのいずれかが欠落している場合は、fail closed とすること。

## 厳格な安全ルール

- 作業前にソースチャンネルとルートスレッドの座標を凍結する。
- ソースチャンネルにルートメッセージを投稿しない。
- ソーススレッドへ投稿する前には毎回、ソースの親メッセージのプリフライトを行う。
- Slack に投稿してよいのはコーディネータだけ。
- 委譲された分析ワーカーは読み取り専用で、発見事項またはメディアに関するメモを返すだけ。
- 修正フェーズのコードワーカーは、その環境から Slack 認証情報と Slack 書き込みアクションがすべて除外されていることを明示的に証明できる場合に限り、編集してよい。それ以外の場合はコーディネータが編集する。
- 子プロンプトは必ず `SendSlackMessage`、`PostToSlack`、`chat.postMessage` およびその他すべての Slack 書き込みを明示的に禁止すること。
- 子に Slack トークン、投稿指示、投稿用のソース座標、外部報告の許可を与えてはならない。
- 子が Slack 書き込みアクセスなしに実行できない場合、起動してはならない。
- ユーティリティ系ボットは証拠源である。人間が明示的に修正を委譲していない限り、修正の担当者ではない。
- 症状を区別可能な決定的な状態として、実 UI 操作を通じて 2 回表示させること。
- 状態確認は観察の裏付けに用いてよい。症状を注入したり強制的に発生させたりしてはならない。
- 再現が確認されない限り、修正コードを書かない。
- 既存のプルリクエストやコミットがある場合、実行を verify モードに切り替える。それらを上書きしてはならない。
- `github.com` のプルリクエスト URL を使うこと。
- キャプチャ、録画、ログ、トークンをソース管理下に置かないこと。
- 委譲された分析では pstack の `principle-guard-the-context-window` を用いること。
- 再現、修正、検証を通じて pstack の `principle-sequence-verifiable-units`、`principle-fix-root-causes`、`principle-prove-it-works` を適用すること。

## 1. ソース座標を凍結する

作業リストを作成したり委譲したりする前に:

1. トリガーのチャンネルが設定済みのソースチャンネルと一致することを要求する。
2. `trigger.thread_ts` が存在すればそれを、なければ `trigger.ts` を `SOURCE_THREAD_TS` とする。
3. 空でない `SOURCE_THREAD_TS` を必須とする。
4. `SOURCE_CHANNEL_ID` と `SOURCE_THREAD_TS` を不変の値として保持する。
5. ソーススレッドを読み、そのルートが上記の座標そのものであることを検証する。
6. ソースの permalink を取得する。

これらの値を、返信のタイムスタンプ、オペレーション側のタイムスタンプ、ステータスメッセージのタイムスタンプなどに置き換えてはならない。

ソースチャンネルへの投稿の前には毎回:

1. 不変の座標でスレッドを読む。
2. 親メッセージが存在し、削除されておらず、現在もソースチャンネルに属していることを確認する。
3. 必ず `channel=SOURCE_CHANNEL_ID` かつ `thread_ts=SOURCE_THREAD_TS` でのみ送信する。
4. 再度スレッドを読み、新メッセージが返信として存在することを検証する。

いずれかのチェックが失敗した場合、何も投稿しない。ルートやフォールバックチャンネルで再試行しない。

## 2. トリアージ契約を待つ

ソーススレッドを、設定済みの判定待ち予算の間監視する。待機中は沈黙を保つ。

次を満たす判定のみ受け入れる:

- 作成者が `slack.triage_identity_user_id` と一致する。
- `SOURCE_THREAD_TS` 配下の返信である。
- 設定済みのマーカーを厳密に 1 つ含む。

公開マーカーの形式:

```text
[benny:bug]
[benny:bug] tracker=https://tracker.example/issue/123
[benny:performance]
[benny:performance] tracker=https://tracker.example/issue/123
[benny:other]
```

`bug` または `performance` の場合のみ処理を進める。任意のトラッカー URL を取り込む。`other`、判定不在、信頼されない作成者、マーカーの競合、タイムアウトの場合は黙って停止する。

このマーカーは、プライベートなボット識別や自由形式の判定マッチングを置き換えるものである。

## 3. 担当および修正アーティファクトのゲートを適用する

作業を始める直前にスレッドを再読する。

### 誰かが明示的に修正中

人物が修正を明確に引き受けた、具体的な実装計画を示した、または別のエージェントに実装・パッチ・修正・プルリクエスト作成を依頼した場合は停止する。

次は修正担当とは見なさない:

- ボットが証拠を要約している。
- ツールがログやチケットを参照している。
- 誰かがボットに診断、説明、調査、再現を依頼している。
- ボットが実装の合意なしに原因の仮説を投稿している。

ボットの存在ではなく、要求されたアクションで判断すること。

### 修正アーティファクトが既に存在する

オープン中のプルリクエストやマージ済みコミットがこの報告を修正している可能性があれば、`references/verify-existing-fix.md` に切り替える。

アーティファクトは、スレッド、トラッカーのイシュー、リポジトリ履歴、プルリクエスト検索のいずれから見つかってもよい。コミットやプルリクエストを伴わない主張は修正アーティファクトではない。

人が担当しているがアーティファクトをまだ提出していない場合は停止する。競合してはならない。

## 4. 任意のオペレーションスレッドを開く

`slack.operations_channel_id` が設定されている場合、コーディネータはそこにルートのステータスメッセージを 1 件作成してよい。これは再現ワークフローで許される唯一のルート投稿である。

その座標を `OPERATIONS_CHANNEL_ID` と `OPERATIONS_THREAD_TS` として保持する。ソース座標と絶対に混同しないこと。

設定済みのプレーン Unicode のステータス文字列を使う。ステータス本文は簡潔に保つ:

- 再現中
- 再現できず
- ブロック中
- 再現済み
- 既存修正の検証中
- 範囲限定の修正を試行中
- ドラフトプルリクエスト作成済み
- 修正が取り込まれず

設定済みの Cursor Slack アクションを優先する。`BENNY_SLACK_BOT_TOKEN` は、このステータスメッセージ 1 件の編集など、限定的に欠落している機能のためにユーザーが設定した場合にのみ使う。トークンをワーカーに露出させないこと。

オペレーションチャンネルが未設定の場合、詳細なステータスはオートメーションの実行出力にとどめる。ソースチャンネルのルートメッセージで代替してはならない。

## 5. コントロールアダプタを読み込みチェックする

`references/control-adapter.md` と `control.feature_map_path` の完成済みマップを読んだ上で、`control.skill_name` が指定するスキルを呼び出す。

報告のユーザーパスに一致するフィーチャーマップのセクションを探す。アプリを操作する前にそれを読む。機能をカバーするセクションがない場合、パスやセレクタを作り出さず、実行をブロック状態として記録する。

7 つの能力すべてを要求する:

1. 設定されたターゲットアプリとテスト環境を起動する。
2. マッピング済み機能に移動し、その文書化された状態を実行する。
3. クリック、入力、キー操作、スクロール、ドラッグ、リサイズ、ナビゲーションで実 UI を操作する。
4. 状態を書き換えずに検査する。
5. スクリーンショットをキャプチャする。
6. 画面録画を開始・停止する。
7. プロセス、セッション、プロファイル、一時データを後片付けする。

アダプタが存在しない、または必須能力のいずれかが欠落している場合、オペレーション状態を blocked にして停止する。スクリーンショット、単体テスト、状態の書き換え、ソース読解を UI 再現と偽ってはならない。

## 6. 報告を精査する

存在する場合はソーススレッド全体とトラッカーのイシューを読む。

収集する項目:

- 正確な操作手順
- 期待される挙動
- 観察された挙動
- 期待と観察が分かれる決定的な状態
- 発生頻度
- バージョン、環境、プラットフォーム
- 添付ファイルとエラーのシグネチャ
- 候補となるコード領域

スクリーンショットと動画を調べる。有用であれば、コード履歴、テストのアイデア、影響範囲マッピング、メディアレビューのために、読み取り専用の並列ワーカーを使う。各ワーカーには狭い質問と Slack 書き込み禁止条項を渡す。

リポジトリを通じて操作パスを追跡する。退行履歴や防御的コードには pstack の `why` スキルを使う。競合する原因仮説を立て、それらを切り分けられる証拠を特定する。

## 7. 再現する

コントロールアダプタを通じてターゲットアプリを起動する。

操作の前に、正しいアプリ、ワークスペース、アカウント、データセット、機能状態であることを確認する。安定したアプリマーカーを使う。ウィンドウ順序や馴染みのあるタイトルだけに頼らない。

報告された操作パスを実 UI 操作で辿る。

再現と呼ぶ前に:

1. 正しい最終状態を言語化する。
2. 壊れた最終状態を言語化する。
3. 両者が分岐する地点まで到達する。
4. 壊れた状態を観察する。
5. 2 回目の試行が独立するよう十分に状態をリセットする。
6. 同じパスを繰り返し、同じ壊れた状態を再度観察する。
7. 可能なら実際の状態値をクロスチェックする。

期待されたダイアログ、読み込み状態、セットアップ手順はバグそのものではない。正しい挙動と壊れた挙動を区別する最終状態をキャプチャする。

設定済みの再現予算を用いる。予算内で症状が再現しない場合、明確に `再現できず` の結果を報告する。環境が必要な能力を提供できない場合、`ブロック中` を報告し、何が欠落していたかを明記する。

## 8. 証拠をキャプチャしレビューする

再現に成功した場合:

- 症状発生までの完全なパスを記録する。
- 壊れた最終状態のスクリーンショットをキャプチャする。
- 正確な手順と観察された状態を記した短いメモを保存する。
- アーティファクトは設定済みの一時成果物ディレクトリに保存する。

読み取り専用のメディアレビュアーに、1 つの質問だけ答えさせる: 証拠は決定的な壊れた状態を視覚的に示しているか?

答えが no または不確かな場合、再現は確認できていないとみなす。より良い証拠をキャプチャするか、`再現できず` を用いる。

詳細な証拠はオペレーションスレッドが設定されている場合のみそこに投稿する。ソース側の更新は簡潔に保つ。

## 9. 再現結果を報告する

まずオペレーションステータスを更新する。

`再現できず` または `ブロック中` の場合、ソーススレッドには何も投稿しない。オペレーションスレッドまたは実行出力が結果を担う。

再現が確認できた場合、ソースプリフライトを実行し、ソーススレッドに最大 1 件の自発的返信を投稿する:

- 問題が再現したことを述べる。
- 存在すればオペレーション側の証拠スレッドをリンクする。
- 短い所見を最大 3 件まで含める。
- 存在すればトラッカーのイシューをリンクする。
- 既定ではオーナーをメンションしない。

証拠を添付するのは、設定済みの Slack アクションが同じソーススレッド内に保持でき、組織の保存ポリシーが許す場合に限る。

設定済みの却下受け付け時間を待つ。セットアップや解釈が誤っていたことを示す人物の指摘があれば、1 回だけ再現をやり直す。有効な却下がないままウィンドウが閉じるまで、修正フェーズを開始しないこと。

## 10. 既存の修正を検証する

修正アーティファクトが存在する場合、`references/verify-existing-fix.md` に従う。

検証では、ベースラインでは症状が現れ、パッチ適用済みビルドでは現れないことを示すこと。両方のパスで実 UI を 2 回ずつ使う。

既存の修正を編集したり、競合するパッチを追加したり、置換のプルリクエストを開いたりしないこと。

## 11. 範囲を限定した修正の適格性を確認する

修正の試行は、次のすべてを満たす場合にのみ行う:

- 結果が純粋に「再現確認済み」である。
- メディアレビューが壊れた最終状態を確認済みである。
- 既存の修正アーティファクトが現れなかった。
- 却下受付期間中に人物が修正を引き受けなかった。
- ランタイム証拠が根本原因を示している。
- 想定される変更が設定済みの修正予算およびリポジトリの範囲に収まる。
- コントロールアダプタがベースラインとパッチ適用済みの両方を実行できる。

いずれかが満たされない場合、再現レポートは維持しつつ、プルリクエストは出さず停止する。

ゲートを通過したら、オペレーションステータスを `範囲限定の修正を試行中` に更新する。

## 12. 根本原因の特定と実装

コーディネータは、すべての Slack 投稿、最終的な差分レビュー、コミット、プルリクエストを所有する。

読み取り専用ワーカーは次を担当できる:

- コードと履歴の追跡
- テストの提案
- 影響範囲のマッピング
- 差分のレビュー
- メディアのレビュー

ワーカーは編集せず、外部書き込みを実行せず、ステータスを投稿せず、修正を所有しない。

このフェーズで厳密にスコープされたコード編集を委譲できるのは、ツール隔離によってワーカーから Slack 認証情報と Slack 書き込みアクションがすべて取り除かれている場合に限る。それでもプロンプトは Slack 書き込み禁止を明示しなければならない。コーディネータは編集をレビューし、必要なテストを実行または検証する。ツール隔離が不確かな場合は、コーディネータが編集する。

ランタイム証拠でメカニズムを確認する。編集前に競合仮説を排除する。

正当化できる最小の変更で根本原因を修正する。

- 安価なローカルテスト対象があれば pstack の `tdd` スキルを呼び出し、修正前に失敗するテストを書く。
- 対象パスが高コスト、不明瞭、あるいは統合テストが重い場合、TDD を省略した理由を述べる。
- 無関係な整理は含めない。
- 変更が設定済みの工数またはリスク予算を超えたら停止する。

## 13. 修正を証明する

元のベースライン証拠を保持する。

パッチ適用済みビルドで:

1. 同じ実 UI パスを実行する。
2. 2 回繰り返す。
3. 壊れた状態が消えていることを示す。
4. 代わりに期待される状態が現れていることを示す。
5. after 録画とスクリーンショットをキャプチャする。
6. ベースラインで用いたのと同じ実際の状態値をクロスチェックする。

コンパイル、ユニットテスト、コードレビュー、妥当そうな差分だけでは after の証拠にならない。

集中テストを実行し、その後、変更された挙動の周辺で影響範囲の軽いテスト (スモーク) を実施する。近接する状態、入力、権限、プラットフォーム、変更が影響し得る失敗パスをカバーする。退行が残っている場合はプルリクエストを出さず停止する。

## 14. ドラフトプルリクエストを開く

修正前後の証拠が揃った後にのみ:

- 最終差分に無関係な変更やシークレットがないか確認する。
- リポジトリの必須チェックを実行する。
- リポジトリのワークフローが許す場合、順序立てた小さなコミットを作成する。
- ドラフトプルリクエストを開く。このワークフローからマージやデプロイは行わない。
- 設定済みのトラッカーイシューを、そのトラッカーがサポートするプルリクエスト構文でリンクする。
- 設定済みの公開 URL 形式を用いる。通常は `https://github.com/{owner}/{repo}/pull/{number}`。
- 再現手順、根本原因、テスト結果、修正前後の証拠、影響範囲チェックを含める。
- プルリクエスト本文とすべての Slack 更新を pstack の `unslop` スキルに通す。

プルリクエスト作成に失敗した場合、成功と主張しないこと。コミットまたはブランチの状態を実行出力に保持し、オペレーションステータスを `修正が取り込まれず` にする。

成功した場合、オペレーションステータスを `ドラフトプルリクエスト作成済み` にし、オペレーションスレッドにプルリクエストのリンク付きで簡潔な返信を 1 件投稿する。ソースチャンネルに 2 つ目のルートを作成したり、自発的なソース返信を投稿しないこと。

## 15. フォローアップと後片付け

設定済みのフォローアップウィンドウの間、オペレーションスレッドを監視する。

- すでに集めた証拠から直接の質問に答える。
- セットアップを無効化する具体的な修正を 1 つ適用し、再現を 1 回だけやり直す。
- 人間同士の調整や雑談には介入しない。
- 停止を求められたら停止する。

必ずコントロールアダプタの後片付け能力を呼び出す。アーティファクトは設定済みの保存ポリシーが許す期間だけ保持する。
