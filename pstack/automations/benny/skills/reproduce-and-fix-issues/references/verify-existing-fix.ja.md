# 既存の修正を検証する

オープン中のプルリクエストやマージ済みコミットが報告を修正している可能性がある場合に、このモードを使う。

既存のアーティファクトが修正を所有している。それを検証する。編集したり、競合するパッチを書いたり、別のプルリクエストを開いたりしないこと。

## アーティファクトの適格性を確認する

次のいずれか 1 つの具体的なアーティファクトを要求する:

- 症状に対処するコード変更を含むオープンプルリクエスト
- マージ済みプルリクエスト
- 該当するコードと意図を伴うマージ済みコミット

プルリクエストやコミットのないスレッド上の主張、トラッカーのステータス、ブランチ名、原因仮説だけでは不十分。

複数のアーティファクトが存在する場合、ソーススレッドやトラッカーからリンクされているものを選ぶ。それ以外は、影響を受けたコードや状態に最も近いものを選び、その理由を述べる。

## 作業ツリーを保護する

リポジトリがサポートしていれば、分離された worktree または別のクリーンなチェックアウトを使う。ユーザーの変更を上書きしないこと。

記録する:

- ベースラインのリビジョン
- パッチ適用済みリビジョン
- プルリクエストまたはコミットの URL
- 両実行で共有するビルドおよび環境入力

通常の `github.com` のプルリクエスト URL を使う。

## ベースラインを測定する

オープンプルリクエストの場合、そのベースブランチをベースラインとして使う。

マージ済みの修正の場合、そのリビジョンがビルドでき、以前の挙動を表すならば、修正の直前のリビジョンを使う。

設定済みのコントロールアダプタを通じて:

1. ベースラインのアプリを起動する。
2. 正しいアプリと環境であることを確認する。
3. 報告された操作パスを実 UI 操作で辿る。
4. 決定的な症状を観察する。
5. リセットして繰り返す。
6. ベースラインの録画、スクリーンショット、状態チェックをキャプチャする。

症状がベースラインで 2 回現れない場合、ベースラインは存在しないとみなす。修正が機能したと主張しないこと。

## パッチ適用済みビルドを測定する

同じ環境とデータで、プルリクエストまたは修正コミットをビルドして実行する。

1. 同じ UI パスを実行する。
2. 2 回繰り返す。
3. 壊れた状態が消えていることを確認する。
4. 期待される状態が現れることを確認する。
5. after 録画、スクリーンショット、同じ状態チェックをキャプチャする。

コンパイルやテストで止めてはならない。after の結果は、動作中のパッチ適用済みアプリから得られたものでなければならない。

## 結果

### 確認済み

ベースラインが 2 回再現し、パッチ適用済みビルドで 2 回解消する。

- オペレーションステータスを「検証済み」とする。
- アーティファクトをリンクする。
- ソースプリフライト後、ソーススレッドに簡潔な返信を 1 件投稿する。
- before と after の結果を含める。
- プルリクエストは出さない。

### 不十分な修正

症状がベースラインとパッチ適用済みの両方で現れる。

- オペレーションステータスを「再現済みだが未修正」とする。
- アーティファクトをリンクし、症状を解消しなかったと明記する。
- 実行中にまだ使っていなければ、通常の再現確認済みのソース更新を投稿する。
- 競合するプルリクエストは出さない。

### 判定不能

ベースラインが再現しない、パッチ適用済みアプリが起動できない、または証拠が決定的な状態を示さない。

- 成功と主張しない。
- どちら半分が測定できなかったかを述べる。
- 結果はオペレーションスレッドまたは実行出力に残す。
- 直接の質問に答える必要がない限り、ソーススレッドに何も投稿しない。

## 後片付け

両方のビルドを停止し、保存ポリシーに従って一時プロファイルとキャプチャを削除し、ユーザーの作業を破棄せずにリポジトリを元の状態に戻す。
