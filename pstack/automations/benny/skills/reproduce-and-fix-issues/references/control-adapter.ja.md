# コントロールアダプタの契約

Benny はすべてのアプリの起動方法や操作方法を知っているわけではない。ユーザーは、ターゲットアプリ向けにこの契約を実装するコントロールスキルまたはアダプタを 1 つ構成しなければならない。

スキル名を `control.skill_name` に設定する。

完成済みのユーザー向けフィーチャーマップのパスを `control.feature_map_path` に設定する。コピー済みのサンプルを編集するのではなく、[`feature-map.example.md`](./feature-map.example.md) を `.cursor/automations/benny/` の外へコピーして記入する。

スキル、フィーチャーマップ、または必須能力のいずれかが欠落、曖昧、または不完全な場合、再現および修正作業は fail closed としなければならない。

## 必須能力

### 起動

要求されたテスト環境で、要求されたアプリのリビジョンを起動する。

入力:

- リポジトリとリビジョン
- ビルドまたは起動モード
- ワークスペース、アカウント、フィクスチャ、機能状態の要件
- アーティファクトディレクトリ
- 完成済みフィーチャーマップのパス

戻り値:

- セッション識別子
- 正しいアプリと環境であることをアダプタがどう確認したか
- 安定したアプリマーカー
- 後続呼び出しが必要とする実行中プロセスまたはターゲットの詳細
- 欠落している能力があればそれ

アダプタは、類似ウィンドウ、シェル、本番インスタンスからターゲットアプリを区別できなければならない。

### UI の操作

実ユーザーのアクションを実行する:

- クリック
- 入力
- キー操作
- スクロール
- ドラッグ
- リサイズ
- アプリコントロールを通じたナビゲーション

ロール、ラベル、安定したセレクタを優先する。座標の使用は、最新のスクリーンショットを撮った後にのみ行う。

各アクションと観察された状態変化を返す。

内部状態を設定したり、隠された API を呼んだり、ストレージへ直接書き込んだり、DOM を操作して症状を作り出したりしてはならない。

### マッピング済みの機能と状態を操作する

アプリを操作する前に、該当するフィーチャーマップのセクションを読む。

アダプタは次を公開しなければならない:

- マッピング済み機能をユーザー視点のパスで巡回する手段。
- その機能用に列挙されたアダプタアクション名を呼び出す手段。
- 該当する場合、default、hover、focus-visible、active、disabled、loading、empty、error、selected、open、expanded、および機能固有の状態との対話。
- 安全なフィクスチャデータ、権限、フラグ、サービス応答、サポートされているテスト制御手段を使った状態の準備。
- 2 回目の独立した再現試行のために機能をリセットする手段。
- フィーチャーマップが指定するスクリーンショット、動画、読み取り専用クロスチェックのキャプチャ。

ロール、アクセシブル名、ARIA 関係、安定したコンポーネントマーカー、目的を表すデータ属性を使うこと。生成された CSS や StyleX クラス、動的ハッシュ、子要素インデックス、脆弱な DOM 位置を使ってはならない。

事前条件の準備は、報告された症状を注入してよいという許可ではない。再現自体は実ユーザーの操作から発生しなければならない。

### 状態の検査

UI が表示する内容を確認するために状態を読む。

例:

- アクセシビリティツリー
- DOM またはビュー階層
- プロセス状態
- ローカルログ
- ネットワークリクエストのステータス
- アプリが公開しているデバッグ状態

検査は読み取り専用。クエリが状態を変える場合、それは「UI の操作」に属し、実ユーザーアクションを表す必要がある。

### スクリーンショット

指定パスへ現在のアプリ状態をキャプチャする。

戻り値:

- ファイルパス
- キャプチャ時刻
- アプリマーカーまたはウィンドウタイトル
- 何が見えるべきかの短い説明

スクリーンショットは、テスト対象が正しいアプリであることを示すだけのアプリクロームを含んでいなければならない。

### 録画

再現パス全体をカバーする画面録画を開始・停止する。

戻り値:

- ファイルパス
- 開始および停止時刻
- キャプチャされたウィンドウまたは領域
- 音声や機微なオーバーレイを除外したかどうか

録画は、セットアップやロード画面のみではなく、決定的な最終状態を示さなければならない。

### 後片付け

アダプタが作成したプロセスやセッションを停止する。

次の使い捨て要素を削除する:

- ブラウザやアプリのプロファイル
- 一時ワークスペース
- アダプタが作成したテストアカウントやフィクスチャ
- デバッグポートやトンネル
- 保存ウィンドウを過ぎたキャプチャ

停止・削除・保持・人に委ねたものを返す。

後片付けはユーザーの作業を削除してはならない。

## アダプタの振る舞い

アダプタは次を満たさなければならない:

- 再現開始前に能力を報告する。
- 自身が操作可能なフィーチャーマップのセクションと、ブロックされているセクションを報告する。
- ベースラインとパッチ適用済みビルドで同じ環境入力を使う。
- 起動失敗は失敗として明示する。
- リトライに上限を設ける。
- シークレットをログやアーティファクトに含めない。
- キャプチャをリポジトリの外に保つ。
- 2 回の再現試行の間に、新鮮またはリセット済みの状態をサポートする。
- ユーザーが明示的に安全なテストアクションを構成していない限り、本番環境を変更しない。

## 環境の読み替え

環境ブロックを宣言する前に、プラットフォーム固有の語を使わずに欠陥を言い直し、利用可能な環境で同じ挙動を安全にテストできるかを問う。

例:

- 特定ブラウザ名は、任意の外部ブラウザを指す場合がある。
- 特定キー名は、設定されたショートカットを指す場合がある。
- 特定のリモートホスト名は、遅延または切断されたリモート対象を指す場合がある。

同じ根底の挙動をテストする場合にのみ、読み替えた試行を用いる。これを読み替え済み証拠としてラベル付けする。欠落している環境が欠陥の一部である場合、正確な再現と呼んではならない。

ハードウェアプロンプト、OS の権限ダイアログ、デバイス専用 API、利用不能なアカウント状態は、真のブロック要因となり得る。

## セットアップチェック

再現オートメーションを有効化する前に、1 回の無害なアダプタチェックを実行する:

1. アプリを起動する。
2. 安定したアプリマーカーを確認する。
3. 完成済みフィーチャーマップのセクションを 1 つ読み込む。
4. その機能にユーザーパス経由で移動する。
5. マッピング済みアダプタアクションを使って使い捨て状態を 1 つ実行する。
6. 結果の状態を検査する。
7. スクリーンショットをキャプチャする。
8. 短いクリップを録画する。
9. 後片付けする。

9 ステップすべてが成功し、かつソースチャンネルへの Slack 投稿が含まれていない場合にのみ、再現作業を有効化する。
