# Benny をセットアップする

Benny は pstack 内に休眠状態のオートメーションパックとして同梱されている。プラグインマニフェストは pstack の通常のスキルルートだけを公開しており、このファイルと 2 つのオペレーショナルファイルはスラッシュスキルではない。

人間は Cursor をパックの `FOR_AGENTS.md` に向けることでセットアップを開始する。ブートストラップフローはパック全体をターゲットリポジトリにコピーし、その後このファイルを `.cursor/automations/benny/skills/setup-benny/SKILL.md` から直接読む。

Benny は外部構成と 2 つのライブ Cursor オートメーションを必要とする。

ユーザーが明示的に指示するまでオートメーションを作成または更新しないこと。シークレット値をプラグインファイル、プロンプト、コミット済み設定に含めないこと。

## 1. パックをコピーし共有 pstack スキルを有効化する

これは Benny 設定を尋ねる前、および組み込みの `/automate` スキルを呼び出す前に行うこと。

どのリポジトリでオートメーションを動かすかを尋ねる。ソースパックは `FOR_AGENTS.md` を含むディレクトリである。配布先は `<target-repository>/.cursor/automations/benny/` である。

ソースパック全体を配布先にマージする:

1. 配布先が存在しない場合は作成する。
2. すべてのソースファイルを同じ相対パスへコピーする。
3. 配布先にのみ存在するファイルを保持する。インストールまたはリフレッシュ中に無関係なファイルを削除しないこと。
4. ユーザー所有の設定、フィーチャーマップ、ルーティングマップは配布先の外に保つ。それらを上書きしないこと。
5. ソース管理対象のファイルに差分がある場合は、差分を確認し、ローカルの編集を破棄せずにマージする。所有権が曖昧な場合は、置き換え前に停止して確認する。
6. 配布先に `FOR_AGENTS.md`、このセットアップファイル、両方のオペレーショナルファイル、その参照先、テンプレートが含まれていることを確認する。

このファイルがすでに配布先から読まれている場合、コピーは完了とみなし、続行前に同じ検証を実行する。

ターゲットリポジトリの `.cursor/settings.json` に pstack を追加する。ファイルまたは `.cursor` ディレクトリが存在しない場合は作成する。

既存の JSON または JSONC に次のエントリをマージする:

```json
{
	"plugins": {
		"pstack": { "enabled": true }
	}
}
```

関係のないトップレベル設定と他のすべてのプラグインエントリを保持する。`plugins.pstack` が既に存在する場合、`enabled` の値だけを変更する。ファイルが JSONC を使っている場合、コメントと有効な JSONC 構文を保持する。編集後にファイルを検証する。

ターゲットプロジェクトをリロードするか、そこをルートとする新規エージェントを起動する。以下の共有 pstack スキルがプロジェクトスコープで解決されることを確認する:

- `why`
- `tdd`
- `unslop`
- `principle-separate-before-serializing-shared-state`
- `principle-minimize-reader-load`
- `principle-guard-the-context-window`
- `principle-sequence-verifiable-units`
- `principle-fix-root-causes`
- `principle-prove-it-works`

現在のセッションやユーザースコープのプラグインからロードされたスキルを数に入れないこと。この確認は、ターゲットリポジトリ内の新規エージェントがプロジェクト設定経由で pstack を受け取ることを示さなければならない。

プロジェクトスコープのプラグインインストールが利用できない、または共有依存のいずれかが解決されない場合、停止して失敗を説明すること。

Benny のファイルは `.cursor/automations/benny/` から直接読まれる。そのディレクトリをプラグインマニフェストに追加しないこと。その `SKILL.md` ファイルがスラッシュスキル一覧に現れることを期待しないこと。

ターゲットリポジトリの `.cursor/settings.json`、`.cursor/automations/benny/`、および参照されるシークレットを含まない設定は、どちらのオートメーションを有効化する前にもコミットされていなければならない旨をユーザーに伝える。ユーザーが指示するまでコミットしないこと。

このチェックが通れば、ライブオートメーションのプロンプトは、安定したリポジトリ相対パスでコミット済みのオペレーショナルファイルを読めるようになる。プラグインキャッシュのパスを埋め込んだり、ファイル内容をコピーしたりしてはならない。

## 2. 設定を自分の環境に合わせる

以下のコピー済みサンプルを開く:

- `../../templates/configuration.example.yaml`
- `../reproduce-and-fix-issues/references/feature-map.example.md`

`.cursor/automations/benny/` の外にユーザー所有のコピーを作成する。これらは設定ファイルであり、パックファイルではない。配置場所の例:

- プロジェクト設定、例えば `.cursor/benny/configuration.yaml`
- プロジェクトのフィーチャーマップ、例えば `.cursor/benny/feature-map.md`
- プロジェクトのルーティングマップ、例えば `.cursor/benny/routing.md`
- ユーザー設定、例えば `~/.config/benny/configuration.yaml`
- ユーザーのフィーチャーマップ、例えば `~/.config/benny/feature-map.md`

オートメーションが再現する可能性のあるすべてのユーザー向け機能について、フィーチャーマップのセクションを 1 つずつ埋める。ユーザー視点を保つこと。実装詳細や現行のコードパスをマップに固定しないこと。

コピー済みサンプルを編集しないこと。パックの更新は、競合レビューの後にソース管理対象のファイルを更新してよいが、ユーザー所有のコピーに触れてはならない。

新規オートメーションのチェックアウトが設定ファイルを読む必要がある場合、ターゲットリポジトリにコミットされたシークレットを含まないファイルを優先する。それ以外は、必要な値をライブプロンプトに言い換えて埋め込む。組み込みの `/automate` スキルが、ファイルがオートメーションを動かすリポジトリにコミットされていることを確認した後にのみ、リポジトリ内ファイルを参照すること。

コミット済みのパックおよび設定ファイルには、安定したリポジトリ相対パスを使うこと。ライブオートメーションからプラグインのソースディレクトリやプラグインキャッシュのパスを参照しないこと。

## 3. 必須項目を埋める

以下について質問または確認する:

- ソース Slack チャンネル ID
- 任意のオペレーションまたはステータスチャンネル ID
- リポジトリ URL とデフォルトブランチ
- トリアージ identity または Slack ユーザー ID
- イシュートラッカーの種類、チーム、プロジェクト、ラベル、受付ステータス
- トラッカーアダプタのスキルまたは MCP アクション
- 任意のルーティングマップパス
- 必須のコントロールスキル名
- 必須のユーザー向けフィーチャーマップのパス
- ステータス絵文字文字列
- プルリクエスト URL 形式
- ポーリングおよび工数予算
- トリアージ、再現、コード作業、メディアレビューのモデル slug

ユーザーの Cursor モデルピッカーまたはサポート済みモデル一覧に表示されているモデル slug のみを使うこと。slug を推測したり、プライベートなデフォルトを流用したりしないこと。

ソースチャンネル、トリアージ identity、リポジトリ、トラッカーアダプタ、コントロールスキル、フィーチャーマップは明示的でなければならない。必須値が曖昧なままならセットアップを失敗とすること。

最終的なオートメーション名、説明、プロンプトシムには pstack の `unslop` スキルを保存前に適用すること。

## 4. 連携機能を確認する

トリアージオートメーションに必要なもの:

- 設定済みソース Slack チャンネルとそのスレッドへの読み取りアクセス
- 同チャンネルでのスレッド返信アクセス
- 報告がメディアを含む場合の添付メタデータとファイルダウンロードアクセス
- 設定済みイシュートラッカーアダプタ経由での検索、読み取り、作成、更新アクセス

再現オートメーションに必要なもの:

- ソーススレッドの読み取りアクセス
- ソースチャンネルでのスレッド返信アクセス
- 設定済みオペレーションチャンネルでの任意の投稿および編集アクセス
- リポジトリの読み取りおよび履歴アクセス
- ドラフトプルリクエストを開けるプルリクエストアクション
- 設定済みコントロールアダプタのスキル

読み取りと投稿には、設定済みの Cursor Slack アクションを優先する。任意の `BENNY_SLACK_BOT_TOKEN` は、オペレーションステータスメッセージ 1 件の編集や添付のダウンロードなどの限定的な隙間を埋めるために使えばよい。値は YAML ではなく、シークレットマネージャまたは環境変数に保存すること。

ドキュメント化されていない連携エンドポイントを使わないこと。

## 5. ルーティングマップを準備する

ユーザーがリルートやオーナーメンションを望む場合:

1. `../triage-issue-reports/references/routing.example.md` を `.cursor/automations/benny/` の外へコピーする。
2. すべてのプレースホルダを公開可能または組織内ローカルの値に置き換える。
3. 既定ではオーナーメンションを無効にする。
4. 設定済みの機能オーナー、または確証のある退行作者の場合にのみメンションを許可する。

ルーティングマップが未設定なら、トリアージは報告を分類してもよいが、宛先やオーナーを推測してはならない。

## 6. コントロールアダプタを検証する

`../reproduce-and-fix-issues/references/control-adapter.md` とユーザーが完成させたフィーチャーマップを読む。

指定されたスキルが次を行えることを確認する:

- ターゲットアプリの起動
- マッピング済みのすべての機能を実 UI 経由で巡回
- 宣言されたアダプタアクションを使ってマッピング済み状態を実行
- 結果を強制せずに状態を検査
- スクリーンショットのキャプチャ
- 録画の開始と停止
- プロセスと一時データの後片付け

いずれかの能力が欠けている場合、再現オートメーションは無効のままにする。再現を行っていないのに行ったと主張するのではなく、fail closed としなければならない。

## 7. ライブオートメーションを準備する

新規作成か、既存オートメーションの構成かを尋ねる。

いずれの経路でも、コピー済みパックの `../../FOR_AGENTS.md` を一次的なユーザーインテントのソースとして読む。これを使って、2 つのトリガー、ツール、指示、成果、共通ルールを理解する。

### 新規作成

一度に 1 つずつオートメーションを作成する。

各オートメーションについて:

1. 対応するコピー済みプロンプトテンプレートを、二次的な社内素材として読む。
2. `FOR_AGENTS.md`、完成した Benny 構成、テンプレートの意図を、完全な自然言語の依頼に起こす。
3. ライブプロンプトに対し、`.cursor/automations/benny/` 配下にコミットされた正確なオペレーショナルファイルを読んで従うよう指示する。
4. プラグインソースやキャッシュのパスではなく、安定したリポジトリ相対パスを使う。オペレーショナルファイルの内容をライブプロンプトにコピーしない。
5. 組み込みの `automate` スキルを読んで従う。
6. `automate` に Slack チャンネル、リポジトリ、連携済み統合を検出させる。
7. コピー済みパックおよび参照された設定ファイルが、オートメーションを動かすリポジトリにコミットされていることを `automate` に確認させる。
8. `automate` にドラフトテーブルを提示させ、承認を得て、準備確認を実施し、Automations エディタを開かせる。
9. 次のオートメーションを開始する前に、このオートメーションのエディタ引き渡しを完了させる。

`automate` に、設定から埋めた以下の完全なトリアージ意図を渡す:

- 名前は `benny-triage`。
- 実行のたびに `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読んで従う。
- 設定済みのソース Slack チャンネルに新しいトップレベル報告が投稿されるたびに起動する。
- 起動元のスレッドを読み、その内部にのみ返信する。
- 設定済みのイシュートラッカー連携を使う。
- 分類、証拠精査、原因追跡、重複判定を行い、明確に新規のバグのみ作成する。
- 1 件のみのスレッド内返信を、設定済みの `[benny:bug]`、`[benny:performance]`、`[benny:other]` のいずれかのマーカーと任意のトラッカー URL で締めくくる。
- ソースチャンネルにルートメッセージを投稿しない。

トリアージのエディタ引き渡しが完了した後、`automate` に次の完全な再現・修正意図を渡す:

- 名前は `benny-reproduce`。
- 実行のたびに `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読んで従う。
- 設定済みソース Slack チャンネルの同じ新規トップレベル報告でトリガーする。
- 設定済みのリポジトリとデフォルトブランチを使う。
- ソーススレッドを読み、その内部にのみ返信する。
- プルリクエスト作成と、設定済みトラッカー、コントロールアダプタ、フィーチャーマップの要件を含める。`automate` が同じリポジトリ内の対象ファイルがコミット済みであることを確認するまで、マッピング済みユーザーパスや状態は言い換えで表現する。
- 信頼されたトリアージマーカーを待ってから行動する。
- マッピング済みの実 UI を通じて同じ症状を 2 回再現し、証拠をキャプチャする。
- 既存の修正を上書きせず検証する。
- 再現が確認された後にのみ、任意で範囲限定の修正を試み、証拠とチェックが通ったらドラフトプルリクエストを開く。
- ソースチャンネルにルートメッセージを投稿しない。

`automate` の Slack、リポジトリ、統合、完成度、認証、ドラフトレビュー、承認、準備確認、エディタ引き渡しの作業を重複して実施しないこと。

### 既存オートメーション

組み込みの `automate` スキルは作成専用である。既存オートメーションの検索、点検、更新には使わないこと。

構成、ルーティング、コントロールアダプタ、フィーチャーマップの検証を終えた後、ユーザーに次の簡潔なエディタチェックリストを渡す。

既存のトリアージオートメーションでは、次を更新する:

- 名前と説明
- `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読む直接指示
- 新規トップレベル Slack 報告のトリガーとソースチャンネル
- Slack スレッドの読み取りと返信機能
- イシュートラッカー連携
- 言い換えによるトリアージ指示、スレッド内返信のみのルール、Benny の判定マーカー

既存の再現オートメーションでは、次を更新する:

- 名前と説明
- `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読む直接指示
- 対応する Slack トリガーとソースチャンネル
- リポジトリとデフォルトブランチ
- Slack スレッドの読み取りと返信機能
- プルリクエストアクション
- トラッカー、コントロールアダプタ、フィーチャーマップの要件
- 言い換えによるマーカー待機、証拠、検証、範囲限定の修正の指示

既存の各オートメーションは、対応する Automations エディタで直接更新するようユーザーに依頼する。置換や複製を作成しないこと。

### 作成の境界

直接的なオートメーションバックエンドサービスやバックエンドオートメーションツールを呼び出さないこと。ドラフトフィールドを持つブラウザ URL を使わないこと。Cursor プロトコルのディープリンクを構築または開かないこと。新規オートメーションの最終化経路は、組み込み `automate` スキルによるレビュー済みの Automations エディタ引き渡しのみである。

エディタ保存後のスレッド安全性テストが通るまで、いずれのオートメーションも有効化しないこと。

## 8. スレッド安全性をテストする

テスト用チャンネルまたは無害なテスト報告を使う。

テスト前に、ターゲットリポジトリの `.cursor/settings.json`、`.cursor/automations/benny/`、および参照されるシークレットを含まない設定ファイルがすべて、オートメーションのチェックアウトで使われるブランチにコミット済みであることを確認する。両方のライブプロンプトが、正確なコミット済みオペレーショナルファイルを指していることを確認する。いずれかが失敗したら停止する。オートメーションはまだ有効化できない旨をユーザーに伝える。

次を検証する:

1. トリアージがルートの `thread_ts` を保持し、ちょうど 1 件の判定を返信として投稿する。
2. 判定に設定済みマーカーが 1 つだけ含まれる。
3. 再現は設定済みのトリアージ identity からのマーカーのみ受け入れる。
4. 再現は同じ不変のソース座標を保つ。
5. ソースチャンネルにルートメッセージが現れない。
6. 委譲ワーカーが Slack 書き込みアクションを一切使えない。
7. 座標の欠落、親メッセージの削除、プリフライト失敗時に、投稿もトラッカーイシューも発生しない。

7 つのチェックがすべて通った後にのみ、通常のトラフィックを有効化する。
