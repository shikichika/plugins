# benny オートメーションの意図

## 自動化したいこと

1 つの Slack イシュー用チャンネル内で連携する、2 つの cursor オートメーションを作りたい。

### オートメーション 1: イシュー報告のトリアージ

- トリガー: 設定したソース Slack チャンネルに誰かが新しいトップレベルの報告を投稿したとき、このオートメーションがその報告に対して起動し、元のスレッド座標を保持し続けること。
- 挙動: スレッドと添付ファイルを読み、報告を bug / performance issue、feature request、question または feedback、あるいは reroute のいずれかに分類し、ルーティング前に担当レイヤーを推定すること。
- トラッカー: 設定したトラッカーで重複を検索し、確度の高い重複は既存チケットを更新し、明確に新規のバグの場合のみチケットを作成すること。
- ツール: Slack スレッドの読み取りと返信権限、設定済みのトラッカー連携、任意のルーティングマップ。
- 成果: ソーススレッドに短い判定結果と `[benny:bug]`、`[benny:performance]`、`[benny:other]` のいずれかを含む返信を、ちょうど 1 件だけ投稿すること。bug または performance のマーカーにはトラッカー URL を含めてもよい。
- 境界: このオートメーションがソースチャンネルにルートメッセージを投稿することは絶対にないこと。

### オートメーション 2: 確認されたバグの再現と修正

- トリガー: 同じ新規トップレベル報告、またはセットアップ時に選択された別の対応トリガーで起動し、元のスレッドで信頼済みのトリアージマーカーを待つこと。
- ゲート: 誰かが明確に修正の担当となった場合は停止すること。既存のプルリクエストやマージ済みコミットが報告を修正している可能性がある場合は、競合する変更ではなく検証を行うこと。
- 挙動: 設定済みのコントロールアダプタとフィーチャーマップを使い、実際の UI を通じて同じ症状を 2 回再現し、スクリーンショット、動画、読み取り専用の状態クロスチェックをキャプチャすること。
- 修正: 既存のプルリクエストを上書きせずに検証すること。再現が確認された後、1 回だけ範囲を限定した根本原因の修正を試みてもよく、テストが低コストなら TDD を使い、影響範囲を軽く確認し、修正前後の証拠が揃った場合にのみドラフトプルリクエストを開くこと。
- ツール: Slack スレッドの読み取りと返信権限、リポジトリと履歴へのアクセス、ドラフトプルリクエストの作成、設定済みトラッカー、コントロールアダプタ。
- 成果: ソーススレッドまたは任意のオペレーション用スレッドに証拠と検証済みの結果を提示し、任意でドラフトプルリクエストを提出すること。更新は簡潔であること。
- 境界: このオートメーションがソースチャンネルにルートメッセージを投稿することは絶対にないこと。

### 共通ルール

- ソースチャンネルとルートスレッドの座標は、実行全体を通して不変であり続けること。
- ユーティリティ系ボットやデバッグ系ボットは証拠として扱い、委譲や修正担当とは見なさないこと。
- サブエージェントの支援は許可するが、Slack への投稿や Slack 認証情報の受け取りは不可であること。
- このパック全体はターゲットリポジトリの `.cursor/automations/benny/` にコミットすること。その `SKILL.md` ファイル群は直接的なオートメーション用指示であり、登録済みプラグインスキルではない。
- pstack は、ターゲットリポジトリにコミットされた `.cursor/settings.json` 経由でのみ有効化し、`why`、`tdd`、`unslop`、必要な原則スキルなどの共有依存のためにのみ利用すること。
- 各ライブオートメーションのプロンプトは、コミット済みのオペレーショナルファイルを直接読むこと。プラグインキャッシュのパス、抜粋コピー、スラッシュスキル検出は使わないこと。
- ユーザー所有の構成、フィーチャーマップ、ルーティングマップ、シークレットは `.cursor/automations/benny/` の外に置き、パックの更新で上書きされないようにすること。
- チャンネル座標、トラッカーアクセス、コントロールアダプタ、フィーチャーマップのいずれかが欠落または不確かな場合、両オートメーションとも fail closed (安全側に停止) すること。
- プルリクエストはドラフトのみとすること。マージやデプロイはしないこと。

### 自分の設定

- ソース Slack チャンネル: `<channel>`
- 任意のオペレーションチャンネル: `<channel or none>`
- リポジトリとデフォルトブランチ: `<repo>`, `<branch>`
- トラッカー: `<type, team, project, labels, intake status>`
- ルーティングマップ: `<path or none>`
- トリアージ identity: `<slack identity>`
- コントロールスキル: `<configured skill or adapter>`
- フィーチャーマップ: `<コピーされたパックの外にあり、同一リポジトリにコミットされたパス、または言い換えるべき挙動>`
- モデル: `<triage, reproduce, code, media review>`
- ステータス絵文字文字列: `<seen, reproducing, reproduced, blocked, fixing, failed, pull request opened>`
- 予算: `<polling, verdict wait, follow-up, repro, rejection, fix>`
- 任意のボットトークン機能: `<none, file download, or editable operations status>`

まずは [`configuration.example.yaml`](./templates/configuration.example.yaml) と [`feature-map.example.md`](./skills/reproduce-and-fix-issues/references/feature-map.example.md) をベースにする。これらはこのパックの外、例えば `.cursor/benny/` 配下にコピーして記入すること。シークレット値はシークレットマネージャまたは環境変数に保管すること。

## エージェント向け

人間は cursor をこのファイルに向けることでセットアップを開始する。検出された benny スラッシュスキルを探したり呼び出したりしないこと。

1. どのリポジトリでオートメーションを動かすかを尋ねる。
2. この `FOR_AGENTS.md` が存在するディレクトリをソースパックとして扱う。
3. ソースパック全体を `<target-repository>/.cursor/automations/benny/` へマージする。
4. 配布先にしか存在しないファイルをすべて保持する。関係のないファイルを削除したり、ユーザー所有の構成、フィーチャーマップ、ルーティングマップを上書きしたりしないこと。
5. ソース管理対象のパスに既存ファイルがあり差分がある場合は、差分を確認し、ローカルの編集を破棄せずにマージする。所有権が曖昧な場合は、置き換え前に停止して確認する。
6. コピー後の `FOR_AGENTS.md` と `skills/setup-benny/SKILL.md` がターゲットリポジトリに存在することを確認する。
7. ターゲットリポジトリ内の `.cursor/automations/benny/skills/setup-benny/SKILL.md` を直接読み、従う。

このエントリをターゲットリポジトリの `.cursor/settings.json` にマージすること:

```json
{
	"plugins": {
		"pstack": { "enabled": true }
	}
}
```

関係のない設定やプラグインはすべて保持すること。既存ファイルが JSONC の場合はコメントと有効な JSONC 構文を保持すること。

ターゲットリポジトリをルートにして新しくエージェントを起動し、検証してほしい。pstack の `why`、`tdd`、`unslop`、および benny が使う原則スキルがプロジェクトスコープで解決されることを確認すること。現在のセッションやユーザースコープのインストール経由でロードされたスキルを数に入れないこと。

プロジェクトスコープのプラグインが利用できない、あるいは共有依存のいずれかが解決されない場合は、停止して何が失敗したかを説明すること。`.cursor/automations/benny/skills/` をプラグインマニフェストに追加しないこと。またその配下のファイルがスラッシュスキルの一覧に現れることを期待しないこと。

`.cursor/settings.json`、`.cursor/automations/benny/`、および参照されるシークレットを含まない設定ファイルは、どちらのオートメーションも有効化する前にコミットされていなければならないことをユーザーに伝えること。ユーザーが明示的に指示するまでオートメーションを作成または更新しないこと。

新規作成時は、トリアージ用と再現・修正用それぞれで組み込みの `/automate` を 1 回ずつ使うこと。最初のオートメーションのドラフトレビュー、承認、準備確認、Automations エディタへの受け渡しをすべて完了してから、次のオートメーションに着手すること。

このインテントと完成した設定をそれぞれのドラフトに言い換えて反映すること。トリアージ用プロンプトは `.cursor/automations/benny/skills/triage-issue-reports/SKILL.md` を読み、従うこと。再現用プロンプトは `.cursor/automations/benny/skills/reproduce-and-fix-issues/SKILL.md` を読み、従うこと。これらリポジトリ相対パスは、`/automate` がそのパスがオートメーションを動かすリポジトリにコミットされていると確認した後にのみ使用すること。

既存のオートメーションの場合、`/automate` を点検や更新に使わないこと。設定を検証した上で、コピー済みセットアップファイル内の簡潔なフィールドチェックリストを提示し、ユーザーが各オートメーションを対応するエディタで直接編集できるようにすること。重複を作らないこと。
