# Arena

何かを起動する前に、各フェーズ（Frame、Fan out、Cross-judge、Pick、Graft、Verify）につき 1 エントリの todolist を開く。

## Phase A: Frame

すべての候補が同じプロンプトを受け取るので、プロンプトが契約になる。

1. 各候補が生み出す成果物を明示する。
2. ルーブリックを導出する。*本* タスクで成功とはどのようなものかを表す、評価可能で具体的な 3〜6 の基準。これはフェーズ D における選者のツールになる。候補はタスクのみを見る。
3. `~/.cursor/rules/pstack-models.mdc` の `arena runners` 行から走者を選ぶ。デフォルトは `claude-fable-5-2-high`、`claude-opus-5-5-high-fast`、`gemini-4-carbon-high`。`auto` または `inherit-parent` エントリは親モデルなので、`model` を省いて `generalPurpose` を起動する。Task ツールが slug を拒否した場合は、同じファミリーで最も近い有効な slug を使うか、シートを落とし、走者を少なくとも 2 つ保ち、その旨を明示する。ファミリーはプレフィックスで決まり、最長一致が勝つ：`claude-fable-*`、`claude-*`、`gemini-*`（先頭の `cursor-` を外した後）。それ以外の slug のファミリーは最初のハイフンまでのテキスト。複数の設計方向のためにはより多く起動し、作業が生成律速で判断に敏感でない場合は同じモデルを繰り返す。各サブエージェントの推論レベルは **poteto-mode** スキルの Subagents セクションに従って選ぶ。
4. 各候補に独自の出力場所を与える（可能なら git worktree、そうでなければ `/tmp/arena-<slug>/candidate-<n>/`）。**separate-before-serializing-shared-state** 原則スキルに従う。

## Phase B: Fan out

1 つのメッセージで N 個すべてのサブエージェントを `run_in_background: true` で起動する。それぞれにタスク、共有グラウンディングへのパス、独自の出力パス、および成果物と候補が検討した代替案と棄却した理由を記した短い根拠を生成する指示を与える。

候補が出力を生成しない場合は、N-1 で進め、ドロップアウトを記録する。

## Phase C: Cross-judge

フェーズ B のすべての候補が完了した後、`~/.cursor/rules/pstack-models.mdc` の `arena cross-judge pool` 行から読み取り専用の審判を 1 つ起動する。デフォルトは `claude-opus-5-5-high-fast`、`gemini-4-carbon-high`。審判は決して親のベンダーから選ばず、Fable はそのチェックにおいて Claude とみなされるので、別ベンダーの最初のエントリを使う。`auto` または `inherit-parent` エントリは親モデル。親のモデルが分からない場合は、最初の実在の slug を使い、ベンダーチェックは行わなかったと明示する。Task ツールが slug を拒否した場合は、同じファミリーで最も近い有効な slug を使い、次にそのようなエントリを使うか、審判をスキップし、その旨を明示する。フェーズ D で読んでいる間に、審判は各候補をパスラベルで識別し、各ルーブリック基準でスコアを付け、ベースを推薦する。

## Phase D: Pick a base

ベースを選ぶ前に、すべての候補を最初から最後まで読む。全体的な感触ではなく、基準ごとにルーブリックに対してスコアを付け、フェーズ C を実行した場合は cross-judge と比較する。ベースの一致は選択の確証となる。不一致は、どちらかが偏っているか、ルーブリックが曖昧だったことを意味する。決定前に両方の根拠を読む。

将来のメンテナがインバリアントを破ることなく最も簡単に拡張できるベースを選ぶ。2 つが同点に感じられる場合は、より清潔な境界か、より小さな API を選ぶ。Laziness Protocol に従う。

## Phase E: Graft

敗者候補をもう一度歩き、ベースに移植する価値があるものを探す。通常は候補ごとに 1〜2 個で、大部分ではない。**redesign-from-first-principles** 原則スキルに従って、1 つの精神モデルの下で結果が一貫するように、各接ぎ木を手作業で折り込む。機械的に貼り付けない。

候補が 1 つの形に収束する場合、それは強い合意である。それを記録し、合意された形を出荷する。接ぎ木は不要である。候補が大きく発散する場合、フェーズ A の仕様が不足している。発散を平均化するのではなく、再フレームして再実行する。

## Phase F: Verify

**prove-it-works** 原則スキルに従って、他の出力と同様に合成された成果物を検証する。arena が見逃した問題を検証が見つけた場合、フェーズ A が間違っていた（再フレームして再実行する）か、ある候補がそれを捉えていて接ぎ木を見逃した（フェーズ E に戻る）のいずれかである。覆い隠さない。

## Outputs

合成された成果物 1 つと、ベース名とその理由、cross-judge の判断またはフェーズ C で審判をスキップしたこと、各接ぎ木とそのソース候補、棄却されたものとその理由、収束またはドロップアウト、検証結果を記した短い合成ノートを隣に添える。
