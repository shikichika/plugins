# verification スキルの保守

機能マップはアプリが変わった瞬間に腐敗する。このスキルは、`/create-verification-skill`（または機能マップを持つ任意のプロジェクトローカル検証スキル）が生成したスキルの保守ループである。厳密性の単位は機能であり、すべての文ではない: すべての機能ファイルをソースからカバーし、すべての機能をライブで実行するが、すべての箇条書きを終端化しない。

## 結果

1 つ選び、どれかを述べる:

- **clean** — すべての機能がソースとライブのカバレッジを得た; 出荷に値するものはない。ブランチなし、PR なし。
- **changed** — 証明された doc、ハーネス、またはマップの修正を 1 つの PR で出荷する。
- **blocked** — カバレッジを完了できなかった、または証明された修正を安全に出荷できなかった。何がブロックしたかを正確に述べる。

## 編集スコープ

検証スキル自身のディレクトリ（その SKILL.md、features/、およびそれが所有するハーネススクリプト）のみを編集する。実行中に製品コードを編集しない: マップが記述するがアプリがもはや行わない動作は、ドキュメントのドリフト（マップを修正）または製品のリグレッション（報告し、ドキュメントで覆い隠さない）のどちらかである。

## パス

0. **ターゲットを特定する。** 保守する検証スキルを見つける: 本体に launch/drive セクションと機能マップを持つプロジェクトローカルスキル（通常は `.cursor/skills/verify-*/`）。候補が複数ある → どれかを尋ねる; ない → ターゲットを発明する代わりに停止して `/create-verification-skill` を指し示す。

1. **インデックスの衛生。** 機能マップの README を読み、兄弟ファイルを glob する。欠落、余分、重複、または死んだエントリを修正する。軽量にし、生成されたインベントリはなし。

2. **ソースウェーブ。** 機能ファイルごとに 1 つの読み取り専用サブエージェントを並行して起動する。各エージェントは、ソースから「このユーザー向け機能はどのように動作するか？」を説明し、引用付きで疑わしいドキュメントのドリフトをフラグし、簡潔なライブ検証レシピを 1 つ返す。子はアプリを駆動せず、ファイルを編集しない。返却の形: 機能の要約／ソースエントリポイント／ドリフトの可能性またはなし／1 つのレシピ。

3. **調整。** すべての機能ファイルに返却された要約がある。重なるレシピを、可能な限り少ないアプリ状態にマージする。引用されたドリフトをスポットチェックする; クリーンな主張を再証明しない。マップから欠落しているユーザー向けサーフェスについて最近の変更をスイープする — 欠落と呼ぶ前に具体的なソースパスを要求する。

4. **ライブパス。** ソースがクリーンに見える場合でも必須。コーディネーターがすべての駆動を所有する; 検証スキル自体の launch モデルに従う — サーバーと UI は 1 つの長期インスタンスを順番に駆動し、短寿命 CLI は駆動ごとに新しい分離されたセッション（スキルの Launch セクションが決定、これではない）。各機能を少なくとも 1 回実行し、失敗が何であれ、パス全体で 3 つの不変条件を保持する: (1) 最後に驚くべきことを行って以来ヘルスチェックしていないインスタンスを決して駆動しない — 最初の駆動前に doctor、セッションが単位の場合は新しいセッションごとに doctor、失敗した駆動後にも doctor、doctor が失敗を見られない場所（健康なプロセス上の詰まった UI 状態）では、望むのではなく、既知の状態にリセットするか再起動する; (2) これまでにキャプチャされた証拠はすべてのクリーンアップを生き残り、名前付きの場所で確認され、仮定されない; (3) 駆動が開始したものは、その駆動の有用性を越えて生き残らない — 失敗したイテレーションの残留物は、セッションが詰まっているか、終了しているか、共有されているかに関わらず（共有インスタンスについては、残留物をクリーンアップし、インスタンスではない）、クリーンアップされる。スキルのドリフトによる doctor の失敗はドリフトである: 編集スコープの下で修正し、一度リトライする — 修正が無効化したものを再起動し、それ以上はしない — パスを `blocked` と呼ぶ前に。到達できない機能は、具体的な前提条件（auth、エンタイトルメント、OS、外部状態）と試みたルートがある場合のみ `verified-unreachable` である; マップがその前提条件を省略している場合、それはドリフトである。トリアージからのハーネス修正は、出荷前にライブで再駆動される。最終的な teardown は、実行の最後の駆動（これらの再証明を含む）の後に行われるので、実行を越えて何も残らない（証拠は残る、スキルに従って）。

5. **トリアージ。** 間違ったまたは欠落したユーザー視点の記述 → ドキュメントのドリフト、修正する。ハーネスが駆動できない動作する動作 → ハーネスのギャップ、修正する; ハーネスの修正は、生成と同じヘルパールールに従う（スクリプトは実行可能、呼び出しはスキル本体に文書化）。実際に壊れているアプリの動作 → 製品のギャップ; ユーザーのために記録し、この PR から除外する。

6. **出荷または停止。** changed の場合: 証明された修正の 1 つの PR、最初に変更された各ファイルを再読。clean または blocked の場合: PR なし、結果とカバレッジを正直に報告する。

カバーされた機能、到達できない前提条件、確認されたドリフト、結果の簡潔な実行ノートをスクラッチの場所に保持する; コミットしない。
