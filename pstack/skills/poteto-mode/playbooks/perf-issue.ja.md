### パフォーマンス課題

**あなたが所有するのは計測のストーリーだ。計画し、レビューし、数値を検証せよ。** すべての修正を計測に紐付け、計測の代わりにソースを読んではならない。

1. 対応する制御スキルを通してベースライントレースを取得する。ベースラインとその後のすべての数値を **benchmark-checklist** スキルで吟味する。
2. コードをトレースして仮説の根拠にする。実行せずに性能上限を主張しない。
   パフォーマンスマントラを、安いものから順に試す:
   1. やらない。結果が使われない作業は、安くするのではなく止める。
   2. やるが、二度やらない。
   3. 回数を減らす。
   4. 後回しにする。
   5. 気付かれないときにやる。
   6. 並行してやる。
   7. より安くやる。

   より早いマントラで目標を満たせたら止める。
3. トレースから修正を計画する。関数の境界をまたぐなら、まず `architect` を用いる。実装は、設定済みの perf-issue モデル（デフォルトは `claude-opus-5-5-xhigh-fast`）を使ってサブエージェントに委譲する。Subagents セクションに従い、ジョブに応じて各サブエージェントの推論レベルを選ぶ。差分をレビューする。修正後のトレースを取得する。
   **sequence-verifiable-units** の原則スキルを適用し、次に進む前に各試行を検証する。
4. 成果物をパースして比較する（JSON を sqlite へ、diff を取る）。"Inconclusive" やサーフェス違いは合格ではない。フラグを立てる。
5. PR で計測値を引用する。
6. **PR を開く** を実行する。

単発の修正ではなく、あるメトリックに対する継続的な改善を目指すなら、Hillclimb プレイブック（`playbooks/hillclimb.md`）を使う。

**返信:** ベースライン値、修正後の値、デルタ、成果物パス。
