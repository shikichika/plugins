### Bug fix

**あなたはこのタスクを所有する。計画、レビュー、検証。** 調査と修正をサブエージェントに委任し、リードにとどまる。Subagents セクションに従って、各サブエージェントの推論レベルをジョブに合わせて選ぶ。

科学的であれ。すべての出荷された行はランタイム証拠にトレースする。「役に立つかもしれない」ベルトとサスペンダーは仮説であり、修正ではない。それは出荷されない。証拠が仮説を反証したとき、それが動機付けたものを元に戻す。証拠が正当化する最小の変更が出荷され、それ以上はない。

1. 制御スキル (譲れないもの) を介して一致する表面で自分で再現する。デバッグまたはインストルメンテーションプロトコルがユーザーに再現を依頼するように言う場合でも。制御表面がターゲットに到達できない明示された具体的な理由がある場合のみ、またそれを限界まで駆動した後にのみユーザーに尋ねる。直接再現しない場合、トリガーを合成し、条件を締め、または点火するまでインストルメントする。
2. 原因を 2 分探索する。候補仮説を形成し、1 つが生き残るまで除外する。影響を受けるサブシステムのトレースと、リグレッション履歴のための **why** スキルで仮説をシードする。各パスで、残りの問題空間を最も削減する分割を取り、ランタイム証拠を取得し、除外する。プログラム状態が不明確なとき、インストルメンテーションまたはロギングを追加し、コードが実行されるにつれて読む。推測しない。Cursor の `/loop` コマンドで長いまたは頑固なハントを駆動する。ステップ 3 の `architect` または `interrogate` ファンアウトの前に、生き残った*メカニズム*をランタイム証拠で確認する。
3. 修正を計画する。関数境界を跨ぐ場合、最初に `architect`。設定した bug-fix モデル (デフォルト `claude-opus-5-5-xhigh-fast`) を使って、特定のスコープでサブエージェントに実装を委任する。
4. 同じ表面で検証する。元の repro が今合格する。「Inconclusive」または間違った表面は合格ではない。フラグを立てる。ユニットテストは分岐動作を示し、バグの不在ではない。
5. 失敗する repro が git 履歴で修正の前にランドするようにコミットをステージする。バグが安価なローカルテストパスを持つ場合は、failing-test-first のケイデンスについて **tdd** スキルを参照する。テストが高コスト、統合中心、または不明確な場合はスキップする。
   これは標準的な **sequence-verifiable-units** 原則スキルであり、失敗するテストが最初で、修正がその上に来る。
6. **Opening a PR** を実行する。

**返信:** 何が壊れたか、根本原因、修正、どう検証したか。failing-then-passing repro 出力をそのまま貼り付ける。
