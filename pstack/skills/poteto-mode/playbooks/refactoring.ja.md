### リファクタリング

**あなたが所有するのは契約だ。構造は変わる。挙動は変わらない。** 挙動を追加する Feature とも、挙動を修正する Bug fix とも異なる。

クリーンアップで欠落機能や真のバグが見つかったら、それらを切り出し、固定した契約に沿って構造変更を先に出荷する。再設計は許容されるが、名を付けて Feature にルーティングする。大規模または横断的な構造作業は **figure-it-out** スキルの管掌だ。本プレイブックは、焦点を絞った〜中規模の変更向けである。

1. まず挙動の契約を固定する。影響サブシステムをトレースして契約を把握し、構造を動かす前に現状の挙動を捕捉する characterization test、スナップショット、または等価性ハーネスを書く。対象領域に既存カバレッジがないなら、構造に触れる前にピンを書く。型検査と lint はピンではない。
2. **principle-model-the-domain** に従い、コードに欠けている構造に名を与える。形状がすでに明確かつ局所的なら、退屈なコードはそのままでよい。形状の作り替えは、間接化を増やすのではなく、分岐や無効状態を削除するものでなければならない。
3. 目指す形状に名を与える。今日ゼロから作るなら、モジュールレイアウト、型、呼び出しグラフがどうあるべきかを述べる（**principle-foundational-thinking**、**principle-redesign-from-first-principles**）。目標が関数境界をまたぐなら、移動前に **architect** スキルを実行して形状を決める。
4. 足す前に引く。デッドコードを削除し、呼び出し元が 1 つのラッパーを畳み、冗長なバリデータを落とし、新しい形状を導入する前に孤立参照を取り除く（**principle-subtract-before-you-add**）。目標形状に到達する最小の変更を出荷する（**principle-laziness-protocol**）。「役立つかもしれない」投機的クリーンアップは revert する。
5. 挙動を保存する小さなステップで動かし、各ステップでピンを緑に保つ。API 再構築では、呼び出し元すべてをマイグレーションし、同じ波の中で旧 API を削除する（**principle-migrate-callers-then-delete-legacy-apis**）。互換性シムも、新旧並行経路も不要。すべてのリネームは実ファイルに対してスポットチェックする。リネームは文字列、散文、バックリファレンス中の使用を静かに見落とす。機械的な編集は、設定済みの refactoring モデル（デフォルトは `claude-opus-5-5-xhigh-fast`）を使い、具体的なスコープ（ファイルパス、動かす名前、保持する挙動）でサブエージェントに委譲する。Subagents セクションに従い、ジョブに応じて各サブエージェントの推論レベルを選ぶ。
6. 実成果物上で挙動が変わっていないことを示す。「コンパイルは通る」では不足（**principle-prove-it-works**）。大きめの再構築では等価性チェックを実行する: 旧対新の出力を diff するスクリプト、新コードに対して再生する記録済みベースライン、または関連する制御スキル経由で対応サーフェスにスモーク実行する。
7. 変更が保持する価値のあるものか確認する。成功指標は読み手の負荷の削減だ（**principle-minimize-reader-load**）。diff が読み手の負荷をどこかで下げないなら、revert する。
8. 小さく順序付けられたコミットにリベースする。引き算のコミット、次に形状の作り替え、その後に残りのクリーンアップ。**sequence-verifiable-units** の原則スキルで整形し、次のスライスに進む前に、各挙動保存スライスを緑に保つ。**PR を開く** を実行する。

**返信:** 変えた構造、それを支えたピン、等価性の証拠、読み手の負荷のデルタ、出荷したものと revert したもの。新規挙動はなし。
