### プロトタイプ

**あなたが所有するのは設計上の意思決定であり、コードではない。プロトタイプは使い捨ての計器だ。本番ビルドは Feature で行う。**

Laziness Protocol の「最小の変更」と検証の基準が反転する唯一のプレイブック。磨き上げより速度、コード品質は問わない、計画もなし。厳密さは、正しい設計を安く選ぶことにある。ユーザーが頼まなかった案も提案し、あるアプローチを捨てて別を試す。

1. プロトタイプが存在意義として決めるべき意思決定をスコープする: どのレイアウト、どのインタラクション、どの密度か。実証的な分岐なら、どの挙動、タイミング、またはアプローチか。意思決定がないならプロトタイプもない。Feature にルーティングする。
2. 設計空間が開かれているなら参考例を集める。先行事例を探し、テーマ・パレット・レイアウトのムードボードを要約し、構築前にユーザーに方向性を選んでもらう。方向性が定まっているなら省略する。
3. 本番ソースから切り離された独立したスクラッチディレクトリで使い捨てを作る。視覚的な意思決定なら、素のままの HTML/CSS/JS、またはアイデアを描画できる最軽量スタック、CDN 依存、ホットリロード付きの dev server を使う。挙動やタイミングに関する意思決定なら、その問いを試す最小限のスクリプトでよい。本番フレームワーク、テスト、抽象化は不要。
4. 代替案を比較するときは、1 つのスイッチャー（ボタンまたはキー押下）の背後に並べ、各バリアントをラベル付けする。これは **exhaust-the-design-space** の原則スキルを安く行うものだ。
5. 対応するサーフェスで検証する。視覚的な意思決定なら、制御スキルで各バリアントをスクリーンショットし、インタラクションを動かす。挙動やタイミングに関する意思決定なら、タイミングをログに取る、出力を印字する、レンダリングを観察するなどして、決めようとしている対象を観察する。ここでは観察自体がテストであり、アサーションではない。
6. 代替案、トレードオフ、推奨案を提示する。アウトプットは意思決定と使い捨ての成果物であり、出荷可能なコードではない。選ばれた方向性を **Feature**（または形状を決める場合は `architect`）に引き渡し、本番ビルドを行う。

**返信:** 探索したバリアント、根拠（視覚的な意思決定ならスクリーンショット、挙動的な意思決定なら観測した出力やタイミング）、トレードオフ、推奨、スクラッチパス。プロトタイプは使い捨てであると明言すること。
