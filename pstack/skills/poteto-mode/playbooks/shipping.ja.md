### シッピング

**あなたが所有するのは着地するものだ。各 PR を独立に検証し、ルートから見て検証済みのランのみを着地させ、その後はスタックから手を引け。**

1. **forge を解決し、着地前に各 PR を独立に検証する。** デフォルトは GitHub CLI（`gh`）。`command -v origin` が成功し、Origin がリポジトリを解決できるなら、全 PR 操作で `origin pr` を使う。そうでなければ `gh` のままで、フォールバックを記録する。Graphite（`gt`）は決して必須にしない。PR 1 つにつき検証者 1 人、各検証者は Cursor のクラウドエージェントで、対応する制御スキル（`cursor-team-kit` の `control-ui` や `control-cli` など）でユーザーと同じ方法で変更を動かし、head を親と対照し、その PR に `PASS`、`PASS+NOTES`、`FAIL` を投稿する。コードを書いていないエージェントからの判定だけが有効だ。作者は意図したものを確認してしまうからである。緑の CI と承認ボットのレビューは判定ではない。どちらもユーザーと同じ方法で変更を動かしていない。
2. **一番下から始まる連続した検証済みランだけを着地させる。** 最も低い未マージ PR から上に歩き、`PASS` または `PASS+NOTES` が付いていない最初の PR で止まる。その下の PR たちがランで、最上位が上限だ。未検証 PR の上にある検証済み PR は待つ。下のコードなしには着地できないからだ。そのコードを含みも必要ともしないブランチの PR は、トランクへ乗せ替えて単独で着地できる。古い判定はその下にコードがある状態で実行されており、トランクにはそれが無いため、まず新しい判定が必要だ。
3. **判定が今もコードを描写しているか再確認する。** 判定はパッチを対象にし、チェーン rebase は、どのチェックも落とさずに上の全 PR を新 SHA に動かす。古い判定を信頼する前に、判定時の SHA と現在の head で `git patch-id` を比較する。差分がテスト、ドキュメント、lint 設定のみなら、2 つの SHA でノイズを除いて同じビルドになる限り、そのレーンの結果は有効だ。ノイズとは、判定時 SHA を 2 度ビルドしても現れる差分、または埋め込まれたコミット SHA のことだ。各種ノイズをファイルとともに報告し、読み手が判断を確認できるようにする。変更自体は新しいチェックとレビューを受ける。古い判定はそれを見ていないからだ。dev server のようにビルド出力を持たないレーンではこれを示せないため、再実行し、ドリフトした他のものも再検証する。
4. **一番下から 1 つずつ着地する。** 常にランの最も低い未マージ PR を `origin pr merge <pr>` または `gh pr merge <pr> --squash` でマージする。Origin では、素のコマンドはその PR より下のすべての PR もマージする。GitHub では、ベースが依然として親のブランチである PR は、トランクではなく親のブランチにマージされる。結果を確認するため PR を読み返す（`origin pr view <pr>` または `gh pr view <pr> --json state,mergedAt,baseRefName`）。マージキューが PR をキューに入れただけでもマージコマンドは成功を返すことがあり、auto-merge 要求はマージではないからだ。着地した PR は、親のブランチではなくトランクをベースとしてマージ済みと読める。`--auto`（Origin の merge-when-ready、GitHub の auto-merge）は、現 head を判定がカバーしている PR にのみ付ける。ready な head であれば何でも着地させてしまうからだ。マージが着地したら、ベースがマージ済みブランチだった PR をトランクに向け直し（`origin pr edit <pr> --base <trunk>` または `gh pr edit <pr> --base <trunk>`）、パッチをマージ結果の上に動かし、`--force-with-lease` で push する。判定はパッチをカバーし、そのコミット群ではないため、ステップ 3 の patch-id ルールが判定の存続を決める。チェックが通り、判定が残っていればマージする。
5. **着地中はスタックに手を触れない。** ステップ 4 で次の PR を動かすことだけが、ブランチやベースへの唯一の変更だ。マージはその瞬間にブランチとベースが持っているものを、判定の有無に関わらず着地させる。GitHub では、`/loop` の下で `scripts/watch-pr/watch-pr --queued-stack` を使ってラン全体を監視し、上限で `COMPLETE` と報告するまで続ける。`--stack-prs` にはラン内 PR 番号を下から上の順で渡し、watcher を再起動するたびに同じリストを渡す。Origin では、`origin pr checks <pr> --watch` が戻るたびに `origin pr view <pr> --checks` で現在の PR を読み返し、上限がマージ済みになるまで続ける。親がマージされたときにベースがトランクに動くのは想定内であり、修復すべきダメージではない。マージが止まったら、何かを変える前に理由を調べる。
6. **上限で止まる。** ランの延長には新しい判定が必要であり、ステップ 1 を新たに通過することになる。

**返信:** 検証済みのランとその上限、各 PR の判定とその発行者、着地したものと確認方法、次のギャップに必要なもの。
