### Autopilot-full

**あなたは判決を所有し、PR は所有しない。1 人のオーナーが各 PR をビルドからマージまで運び、コードを書いていないあなたの swarm がランドするコードを証明するまで何もマージされない。**

判決は 1 つのパッチをカバーし、グリーン CI は 1 つの head をカバーする。ステップ 4 は一度フルスワームを実行し、大きな変更に対してのみ再実行する。`playbooks/shipping.md` の patch-id ルールはレーンの結果を運ぶことができ、すべての新しい head は自身のグリーン CI が必要である。

1. **オペレーターのゲートが最初に来る。** グラントはキューのアイテムのみをカバーするので、オペレーターが自分のものと名付けたアイテムとキューの外の PR はマージ可能で停止する。プランを述べる要求は go ではない。
2. **PR ごとに 1 人のオーナーを生成し、代替が見つけられる場所にその作業を保つ。** プログラムのために forge を一度解決する。GitHub CLI (`gh`) がデフォルト。`command -v origin` が成功し、Origin がリポジトリを解決できる場合、すべての PR 操作に `origin pr` を使用する。そうでなければ `gh` のままにして、フォールバックを記録する。Graphite (`gt`) を決して必須にしない。各オーナーは Cursor クラウドエージェントで、ビルドし、`playbooks/opening-a-pr.md` に従って PR を開き、実際のアーティファクトで変更を証明し、`playbooks/babysit.md` に従ってグリーンまでベビーシットし、ステップ 4 と 5 がクリアしたらマージする。そのプレイブックがリベースを報告するように言う場所で、オーナーは自分のブランチをリベースし、`git push --force-with-lease` で公開する。

   作業と並行して CI とボットが実行されるように PR を早く開く。コードは、slop-strip (`cursor-team-kit` プラグインの `deslop` スキル (`/deslop`)) と `/no-comments` パスの後にのみ準備完了になり、したがってフルスワームは完成したコードで実行される。次に、現在のトランクにリベースし、セルフプルーフの前に code-ready head を報告し、検証がパッチがランドするベースで実行されるようにする。後のすべての head を報告し、セルフプルーフ、CI、ベビーシットが完了したら merge-ready を報告する。修正ラウンドは、トランクが競合しない限り、CI を壊すか、同じファイルへの既知の並行変更をランドさせない限り、そのベースに留まる。なぜなら各リベースは CI を再起動するからである。code-ready push の前と、検証器を必要とする後の push の前に、コミットされた head で触れたパスのリポジトリのチェックを実行する。

   VM が死ぬと想定する。開始直後にプッシュし、**show-me-your-work** スキルに従ってルートエージェントのストア (システムプロンプト内のパス) で決定トレイルを開始し、次を開始する前に完了した各ユニットをプッシュする。サブエージェントを生成する者は、その id、状態、およびその種類の過去の実行からの stuck-after ランタイムをそのストアに記録し、親が死んだ場合にルートがそれをプローブできるようにする。あなた自身のブランチのみを強制プッシュし、最後にプッシュまたは引き継いだ SHA にピン留めされた `--force-with-lease` を使用し、自分で行っていない任意の push で、停止してルートに報告する。
3. **オーナーをトランクから並列に実行し、スタックしない。** 各 PR がそれ自身でランドするように。
4. **一度 swarm-verify する。** フルスワームは code-ready head で一度実行される。別のフルスワームは、新しい動作、再設計、または大きな新しい diff のためにのみ実行される。リベース、マージ競合の解決、または小さな修正は新しい head で単一の検証器を取り、文言のみの変更はなしを取る。**swarm** スキルに従って code-ready SHA で独立した検証器をファンアウトする。それらはゲートを再実行し、その制御スキル (`cursor-team-kit` の `control-ui` または `control-cli` など) または名前付きドライバーを介して実際の表面で負荷ベアリング動作をライブで証明し、diff を監査する。判決はライブレーンなしでは、または merge-ready レポートの領収書を監査する前には、クリーンではない。なぜなら、どのレーンもチェックしていない主張を信頼しないからである。

   示せる問題でのみ PR をブロックし、head での失敗した実行、または PR が間違ったものにしたドキュメント行を持つ。PR のベース (トランクまたはスタック内のその下の PR) が既に持つ問題は、PR がそれをコピーするか新しく到達しない限りブロックしない。ユーザーがぶつかるバグ、失敗したゲート、または間違った出荷済みドキュメントのみがブロックし、他のすべてはフォローアップに行く。
5. **オーナーは、ランドするトランクでテストされた、あなたが検証したもののみマージする。** グリーン CI 単独では決してマージを承認しない。swarm のレーンが開始されたら、マージ準備は現在のトランクにリベースし、新しい head を報告し、グリーン CI を待つ。

   マージの直前に、トランクをフェッチし、その変更がパッチに影響しうるかを尋ねる。なぜなら、すべてのトランクの動きに対してリベースすることは決して終わらないからである。ランドしようとするコードがテストされていない場合は、リベースして CI を待つ (競合、両サイドが変更したファイル、または PR のどのチェックが実行されるかへの変更など)。両サイドが変更したロックファイルは、マージ結果で凍結インストールが合格し、PR が変更するパッケージが head で解決するようにそこで解決する場合、リベースは不要である。なぜなら、そのインストールはランドするロックファイルをテストし、失敗したインストールはリベースが修復する必要があることを意味するからである。トランクがパッチの呼び出し元またはパッチが依存するもの (呼び出すコードまたは依存バージョンなど) を変更した場合、マージ結果でパッチのチェックを実行し、合格でマージする。それ以外はマージする。マージ準備を超えてトランクが 3 回目のリベースを強制する場合、保留して衝突する作業を順序付けるルートに報告する。
6. **ルート層を実行する。** 予算の引き上げや許可リストエントリなど、ゲートを緩めるものは、検証器の証明とあなたの新鮮なカウンターサインが必要である。なぜなら、オーナーはグリーンを望む人だからである。承認をカバーするグラントの下で、そのカウンターサインは承認であり、オーナーのそれの記録は、レーンがチェックするためにあなたのカウンターサインを指す。無効化またはソフト失敗したチェックは常に出てくる。なぜなら、それはすべてのケースをガードするのをやめるからである。forge が強制する承認を与えたりバイパスしたりしない。なぜならカウンターサインはそれをカバーしないからである。

   オペレーターの go で、`/loop 1h` を装備して、委任された作業が残っていなくなるまで監査する。なぜなら、長い実行はドリフトし、エージェントは静かに停滞するからである。各 tick はトランクからこのプレイブックを再読し、オーナーに記録させることで、報告されていない head または記録されていないエージェントなどのドリフトを修正する。なぜなら、ドリフトは記録のギャップであり停滞ではないからである。葉のレーンまで各エージェントをプローブし、各を副作用で判断する。なぜなら、ステータステキストとサマリは stuck な子を隠すことができるからである。エラーが出るか、ターンを開始できないか、stuck-after ランタイムを超えて新しいものを何も表示しないエージェントは stuck であり、最初の tick でプッシュもトレイル行の書き込みもしていないオーナーもそうである。あなたまたはオペレーターを待っているものは stuck ではないので、答える。stuck なエージェントは、その停止がランドするのを待たずに直ちに置き換える。オペレーターのために何かを変えた tick は、**ketchup** スキルに従って彼らをキャッチアップして終わり、何も変えなかったものは静かにとどまる。
7. **オペレーターの停止で直ちにスタンドダウンする。** 保留は各オーナーにゼロ書き込み命令として届く。各は現在の位置を報告し、オペレーターが解放するまでそのブリーフを保持する。

**返信:** **ketchup** スキルに従ってオペレーターをキャッチアップし、各 PR の状態と判決、何がマージされたか、カウンターサインと理由、未解決のオペレーターゲート、駐車されたフォローアップを、各 PR とトレイルへのリンクとともにカバーする。
