# Bugbot トリアージ

Babysit プレイブック (`../playbooks/babysit.md`) が Bugbot またはレビュー自動化コメントを扱うときにこのリファレンスを使用します。目標はデフォルトで Bugbot を無視することではありません。目標は、すべてのコメントを必須のコード変更として扱うのをやめることです。

## 判断基準

行動する前に各 Bugbot スレッドを分類する:

- `fix`: コメントがもっともらしい正しさ、セキュリティ、プライバシー、データ損失、認証、課金、マイグレーション、冪等性、レース、または出荷済み動作の問題を特定している。最も下の所有 PR で修正し、コミット SHA で返信してスレッドを解決する。
- `dismiss`: コメントが文書化された低リスクのノイジーパターンに一致し、現在のコードまたはコンテキストが懸念はコード変更を必要としないことを証明する。短い理由で返信してスレッドを解決する。
- `ask`: コメントが斬新、高深刻度、セキュリティ/プライバシー/データ関連、または曖昧である。推測する代わりにユーザーに尋ねる。

疑わしいときは尋ねる。ノイジーなコード品質コメントをスキップするのは安価だが、実際のデータまたはセキュリティバグをスキップするのは安くありません。

## 学習したパターンのフォーマット

将来のパターンをこの形で追加する:

```markdown
### <short pattern name>

- Confidence: candidate | recurring | strong
- Skip when: <conditions that must be true>
- Do not skip when: <risk boundaries>
- Example signal: <phrases or code context that identify the pattern>
- Source: <PR/comment URL or short historical note>
```

1つか2つの例には `candidate` を使用する。複数の実際の却下の後に `recurring` を使用する。`strong` は、パターンが狭く、繰り返し検証され、低リスクの場合のみ使用する。

## 繰り返しスキップ候補

### 意図的な UI またはデザインシステムの視覚的変更

- Confidence: candidate
- Skip when: PR の説明、スクリーンショット、デザインレビュー、または近くのコードが視覚的変更を明示し、Bugbot コメントが共有された視覚的デフォルトが変更されたことを言い直しているだけ。
- Do not skip when: コメントがアクセシビリティ、フォーカスの可視性、キーボードナビゲーション、色のコントラスト、または PR が意図的に変更しなかったコンポーネント API 契約を指す。
- Example signal: フォーカスアウトライン、ボタンサイズ、間隔、または共有コンポーネントの視覚的デフォルトに関するコメントで、所有者が「intentional」または「intended」と返信するもの。

### Bugbot が見えないアップスタックまたはスタックローカルな使用

- Confidence: candidate
- Skip when: Bugbot がエクスポート、コンポーネント、ヘルパー、またはファイルを未使用としてフラグを立てるが、アクティブな forge の PR リストと diff、アップスタックの diff、または PR コンテキストが、スタック内の後の PR で使用されていることを示している。
- Do not skip when: 現在の PR がスタックの一部ではない、シンボルが公開 API、または想定されるアップスタック使用が検証できない。
- Example signal: 「Exported component is never used」で、人間が「used upstack」と返信。

### 並列実装中の一時的な重複

- Confidence: candidate
- Skip when: PR が意図的に少量のコードを重複させ、削除、置換、または証明中の古いパスと並行して新しいパスを保つ。
- Do not skip when: 重複したコードがセキュリティ、課金、データアクセス、API 動作を変更するか、長命な共有抽象化が明確にリスクを減らす。
- Example signal: 「Significant duplication」または「duplicated validation logic」で、所有者が古いパスは削除されるか、重複ロジックは意図的にローカルであると説明。

### 既存のフレームワークまたはコンポーネントの不変条件が警告をカバー

- Confidence: candidate
- Skip when: 懸念が既に共有コンポーネント、フレームワーク契約、型不変条件、または現在の diff または近くのコードに見える単一の情報源によって保証されている。
- Do not skip when: 不変条件が仮定されているが強制されていない、タイミングに依存する、または値が分岐しうる async/状態の境界を跨ぐ。
- Example signal: 共有ポップオーバーがビューポート境界を強制するときの内部ポップオーバーの最大高さ不足についてのコメント、またはローカルにチェックされた値と渡された値が同じソースを共有するヌル許容値。

### 所有者が宣言したフォローアップまたは延期されたクリーンアップ

- Confidence: candidate
- Skip when: PR 所有者が明示的に、問題は既知のフォローアップであり、動作は現在の PR によって悪化せず、コメントは高リスク領域についてではないと述べている。
- Do not skip when: エージェントが所有者の入力なしで行動している、問題が中/高深刻度の製品動作、または遅延によって新しいリグレッションがマージされる。
- Example signal: 「I'll worry about that later」または「we'll delete this eventually」。

### 自己撤回または明示的な偽陽性ルールコメント

- Confidence: recurring
- Skip when: コメント本文または後の Bugbot 返信が、発見が撤回された、準拠している、または偽陽性であると明示的に述べ、エージェントがローカルに関連ルールを検証できる。
- Do not skip when: 唯一の証拠が、説明なしで高リスク問題について「false positive」と言っている人間である。
- Example signal: ファイルが既に準拠していると本文に書かれているファイル名ルールコメント。

## デフォルトで尋ねる

以前の PR が類似のものを却下した場合でも、これらのカテゴリを自動スキップしないでください:

- セキュリティ、プライバシー、認証、課金、データ保持、トレーニングデータ、および権限境界の発見。
- 高深刻度の発見。
- マイグレーション、スキーマ、冪等性、並行性、およびクロスシステム動作の発見。
- 推奨された修正が小さく、製品の意図を変えずに明確にリスクを減らすコメント。

過去のデータは、人間が時々セキュリティ/データフローコメントを却下することを示しました。それらをチーム全体のスキップルールではなく、所有者の判断として扱います。

## 最近のベビーシッティングからの候補学習

ベビーシッティング中または後に、チームに役立つように見えるがまだ成熟していないときに、ここに新しい候補学習を追加します。複数の PR がパターンを確認したら、繰り返し候補を上記のセクションに昇格させることを好みます。

### ネイティブブラウザ動作の手動再実装

- Confidence: candidate
- Skip when: 実質的に決してしない。diff がネイティブブラウザ動作を手動の等価物に置き換える場合（ネイティブ sticky → JS 位置クローン、ネイティブスクロールターゲティング → 転送されたホイール/タッチイベント、ペイント順序の遮蔽 → マスク/clip-path）、そのコードに対する Bugbot のロジックバグの発見は一貫して正当である。
- Do not skip when: 発見がイベント転送のギャップ (wheel deltaMode、タッチパン、エッジでのスクロールチェーン、タップスロップ)、マスク/クリップのヒットテスト不一致、または observer-vs-React 状態タイミングレースに関するもの。デフォルトで修正する。
- Example signal: 「masks do not affect hit-testing」、「overlay blocks wheel scroll」、「ignores deltaMode」、「runs in the IntersectionObserver callback before React applies state」。
- Source: 1つの sticky-occlusion PR: 6回の Bugbot パス、約 18 件の発見、すべて却下ではなく修正された。

### 契約テストドリフトの主張は安価に検証可能 — まずテストを実行する

- Confidence: candidate
- Skip when: 検証自体を決してスキップしない。コマンド1つのコストで済む。PR
  がプロトコルまたはドキュメントの散文 (SKILL.md 上の正規表現、ドキュメントの文言のスナップショット) を固定する契約テストを出荷し、Bugbot が「テストがもはやドキュメントと一致しない」(またはその逆) と主張する場合、分類する前に PR 先端でそのテストを実行する。赤い実行は主張を経験的に確認し、緑の実行は却下返信のための具体的な反証である。
- Do not skip when: n/a — これは却下パターンではなく検証ショートカットである。繰り返しパス lean-dismiss ヒューリスティックがここで誤作動することに注意: 散文固定テストは、以前の修正ラウンドが散文を編集するためにドリフトする。
- Example signal: 以前の修正コミットが固定された文章を再言葉遣いした PR 上の「Contract test omits the pre-fix wait」で、先端で実行されたテストが引用されたアサーションで正確に失敗した。
- Source: 8 回の Bugbot パスを持つ 1 つの散文固定 PR で、すべての以前のパスが修正されて解決されたにもかかわらず、パス 7 で主張が実際だった。

### 同じ PR で後に既に修正された古いセキュリティレビューの発見

- Confidence: candidate
- Skip when: エージェントセキュリティレビュー (または類似) が authz/検証呼び出しの欠落を主張し、現在の PR 先端が明らかにその正確なゲートを (テストとともに) 含み、通常はレビュー実行後の後のハードニングコミットで追加されている。
- Do not skip when: 引用されたヘルパーが議論中のプリンシパルに対して no-op である、チェックがガードする副作用の後に実行される、または主張されたプリンシパルのカバレッジが欠落している。
- Example signal: 正確なガードが先端上の副作用の前に既に呼び出されている間の HIGH「missing authorization check」発見。
- Source: 1つの Webhook エンドポイント PR で、ハードニングコミットがレビュー実行の後。

### 意図的に狭いエラー条件を広げると実際のエラーが隠される

- Confidence: candidate
- Skip when: 発見が狭いエラー条件 (特定の `errno`、エラーコード、またはステータスクラス) を catch-all に広げるよう求め、その狭さが実際の区別をエンコードしている。標準的な形は `ENOENT` でゲートされた依存性フォールバックである:「バイナリがインストールされていない」は「コマンドが実行されて失敗した」とは異なる状況である。任意の非ゼロ終了でリトライすると、正当な失敗 (見つからない、期限切れの認証、ネットワーク) をフォールバックに対して再実行し、フォールバックのエラーを報告し、真のエラーを隠す。
- Do not skip when: 狭い条件が同じカテゴリ (`EACCES` のような別の「バイナリ使用不能」errno、別のトランスポートレベルの障害) のケースを見逃す、未処理のパスがデータを失うか部分状態を残す、または再試行が冪等でありかつ元のエラーがまだ表面化している。
- Example signal: 失敗した操作のためではなく欠落した依存関係のためにフォールバックが存在するコードを指す「only retries when X fails with ENOENT … never tries the fallback even when a working Y exists」。
- Source: フォールバックが失敗したコマンドのためではなく欠落したバイナリのために存在する 1 つの CLI 名前変更 PR。
