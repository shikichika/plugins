# Blast radius

変更が出荷される前に、他の場所で何を壊すかを見つける。「X の爆発半径」、「これは何を壊し得るか」、またはまだ信頼できない小さな diff のレビューに使う。

`how` と `why` の仲間。`how` はコードが何をするかを教える。`why` はそれがなぜその形になっているかを教える。Blast radius は他の場所で何を壊すかを教える。

呼び出し元のリストアップは仕事ではない。エージェントは一秒でそれを grep できる。仕事は grep が見せない破損である。

## 自分の文書を信頼しない

正しく聞こえる blast-radius 文書は無価値である。真実であろうとなかろうと、説得力があるように読める。だから文書を渡さない。全体が依存している 1 つか 2 つの事実を見つけ、コードを実行して証明する。

### どれくらい確信があるか

変更の安全性が依存する各事実について、このリストをできるだけ安く下げ、どこで止まったかを明示する。

1. あなたがそう言った。それ自体は無価値。
2. あなたは行を指した。実際の `file:line`、またはライブラリ自身のソース。
3. あなたは悪いケースが起こり得ないことを示した。失敗を一歩ずつ歩き、到達しないことを確認した。
4. あなたはそれを実行した。実コードを呼び出し、間違っている場合に大声で失敗するスクリプトまたはテスト。
5. あなたは実行中のアプリで再現した。

ステップ 4 は通常、アプリが出荷するのと同じライブラリをインポートし、心配している正確な関数を呼び出す小さなスクリプトである。

## 手順

1. 変更を読む。diff、追加・変更・削除するシンボル、diff が明示しない部分を含めて、今何が異なるか。PR とそのコミットを引っ張る。
2. 安全の根拠となる 1 つの事実を見つける。危険に見える変更のほとんどは、「この呼び出しはすでに死んだキャッシュエントリのみをドロップし、他に何もしない」のような単一の事実のおかげで安全である。その事実を見つける。それが成立すれば、ほとんどのリスキーなケースは一度にクリアされる。長い「かもしれない」リストではなく、ここに時間を費やす。
3. grep が止まる場所を見る。呼び出すライブラリのソースを読み、固定されたバージョンとローカルパッチを確認する。物事がいつ実行されるかを突き止める：マイクロタスク、アンマウントとティアダウン、Solid vs React。シンボル検索が見逃すものを追跡する：API が返す JSON、DB カラム、ワイヤ形式、同じバイトを読む別言語、feature flag、3 ホップ下流のコード。
4. 各リスクについて正直になる。実際に起こる可能性と、起こった場合の実際のコストを与える。確認したリスクを保持する。チェックしてクリアしたものは別途リストする。実際の `file:line` を引用し、何も見つけない検索も答えであり、呼び出し元や API を作り上げない。
5. その 1 つの事実を証明する。実コードを実行するスクリプトまたはテストを書き、実行し、何が起こったかを貼り付ける。
6. 大きい、または広い変更の場合は、`arena` として実行する。複数のモデルに同じ質問をし、回答をマージする。異なるモデルは異なる実バグを捉える。

## 何を渡すか

- **何をするか。** 明らかでない部分を含めて、何が変わったか。
- **安全の根拠となる 1 つの事実。** それを述べ、どのステップまで到達したかを明示し、証明を示す。証明できなかった場合は、未証明と書く。
- **リスク。** 各リスクはどのように壊れるか、`file:line`、可能性と重大度、確認方法を名指しする。重要なものには証明を貼り付ける。
- **クリア済み。** チェックしたものとそれが問題ない理由。
- **マージする前に。** 自分が書いたスクリプトを含め、実バグを捉える最も安価なテストまたは再現。

`unslop` を介して書き、実コードを引用し、公開する前にプライベートなものをすべて剥がす。

**返信：** 上記の文書、その 1 つの安全の事実が証明されたか未証明としてマークされたもの。
