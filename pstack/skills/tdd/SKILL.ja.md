# TDD によるバグ修正

明確で安価なテスト経路を持つバグを修正するときは、プロダクションコードを変更する前に、壊れた挙動を実行可能にする。目標は、修正前に失敗し、修正後に通過する、焦点を絞ったリグレッションテストである。

実用的でない場合にテストを強行してはならない。利用可能なテストが、広範なハーネスのセットアップ、脆いモック、低速なエンドツーエンドインフラ、プロダクション専用の状態、曖昧な再現手順、または無関係なフィクスチャの大規模な変更を必要とする場合、新しいテストの追加はスキップし、代わりに最も近い有用な検証を用いる。

## ワークフロー

1. **バグを理解する。** 意図された挙動、現在の挙動、影響を受ける経路、最小の観測可能な再現手順を特定する。
2. **最も狭い実行可能なチェックを選ぶ。** そのコードパスで既に使用されている、最も近い単体、コンポーネント、統合、またはリグレッションテストを優先する。実用的なテスト経路が明らかでない場合、ワークフローを満たすためだけに一から作成してはならない。
3. **失敗するテストを先に書く。** バグを捕捉できたであろう最小の焦点を絞ったテストを追加する。テストは現在の実装を鏡写しにするのではなく、意図された挙動を符号化すべきである。
4. **修正前に新しいテストを実行する。** 意図した理由で失敗することを確認する。無関係な理由で通過または失敗する場合、実装を編集する前にテストまたは再現手順を修正する。
5. **バグを修正する。** 周辺の契約を保ったまま、意図された挙動を満たす最小のプロダクション変更を行う。
6. **リグレッションテストを再実行する。** テストが通過することを確認する。

## 失敗するテストが非実用的な場合

代わりに最も近い実行可能なリグレッションチェックを使用する。例えば、対象を絞ったスクリプト、手動の再現コマンド、ブラウザ自動化、スナップショット比較、ログアサーション、焦点を絞った統合チェックなどである。

悪いテストよりは新しいテストを作らない方がよい。悪いテストとは、主にモックをテストするもの、現在の実装詳細を符号化するもの、タイミングや無関係なグローバル状態に依存するもの、小さな修正のために高価なインフラを必要とするもの、または修正の証明後すぐに削除されるようなものを指す。

## ガードレール

- 誤った実装に合わせるためだけにテストを変更してはならない。
- 期待される挙動が実際に変化し、その理由が明確でない限り、既存のアサーションを弱めてはならない。
- リグレッションテストはバグに焦点を絞ったままにする。広範なフィクスチャの変更や無関係なカバレッジ拡張を避ける。
- バグが不安定（flaky）である場合、可能な限りテストを決定的にし、固定されるシグナルを文書化する。
- バグがより広範な失敗のクラスを露呈する場合、まず焦点を絞ったリグレッション経路をマージし、その後に追加の兄弟カバレッジを検討する。

## 最終報告

結果だけでなく証跡を報告する。

- 修正前に失敗したテストまたは実行可能なチェックと、生じた失敗を名指しする。
- 修正後に通過したテスト実行と、周辺で行った検証を名指しする。
- 修正前の失敗の証跡を示せなかった場合は、その理由を述べ、代わりに使用した最も近いリグレッションチェックを説明する。
