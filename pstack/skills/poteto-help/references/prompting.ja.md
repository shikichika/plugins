# プロンプトを言語化する

プロンプトは意図と完了のチェックを述べます。プレイブックがステップを供給するので、平易な数文が仕様書に勝ります。

## 入れるもの

- ゴール。何が悪いか、またはユーザーが何を望むかを述べる。
- 完了チェック。合否判定できるもの。「もっと良くして」と時間は、チェックではない。
- 示す証拠。実際のコマンド出力、フローの動画、保存された値、または前後の数値を求める。
- ユーザーが既に知っていること。症状、再現ステップ、ログ、またはリンクがあればエージェントの検索を省ける。
- 実際の制約。「まず再現」、「まだコードを変更しない」、「動作変更ゼロ」、「進める前にレビューさせて」はそれぞれエージェントの行動を変える。

## 省くもの

- やり方。達成すべきことを述べ、エージェントにより良い方法を見つける余地を残す。
- スキルまたはステップのリスト。手書きの順序はプレイブックが保持するステップを落としたり順序を変えたりする。1つの選択を上書きするためにのみスキルを名指しする。
- ユーザーの原因の推測。エージェントが問題を言い直すまでは。推測を述べると探索が狭まる。

## 最初にコンテキストをロードする

- 騒がしいレポートに対しては、エージェントに何かする前に自分の言葉で平易な英語で根本的な問題を言い直すよう求める。誤読はコードが存在する前に現れる。
- 新しいチャットでは、トピックに関する以前の作業を `/recall` する。古いチャットには新しいエージェントが欠いているコンテキストがある。
- 不慣れなコードへの変更の前に、メカニズムについて `/how` に、理由について `/why` に尋ねる。トレースされたモデルを持たないエージェントは最初のそれっぽい場所で症状を修正する。
- `/teach` に選択の論拠を作らせる（例: 「症状ではなく原因を修正していることを納得させて」）。論拠はサマリより確認しやすい。

## プランの前に設計する

- 最初のデザインを決して採用しない。いくつかの選択肢のプロトタイプを、UI の場合はスクリーンショットまたは動画とともに求め、証拠から選ぶ。
- プロトタイプに未解決の質問に答えさせる。レビュアーは起こらないリスクを発明するので、抽象的なプランを敵対的にレビューしない。
- 共有パッケージまたは API に対しては、まず README またはチュートリアルを求め、そこからコードに戻る。ドキュメントはエージェントが自分自身をチェックするターゲットになる。
- 設計が決着した後にのみプランを求める。プランの各ステップはチェックで終わる。

## 短くフォローアップする

- 「do it」、「continue」、「keep going until done」はチャットがタスクを保持していれば完全なプロンプトになる。
- 主題が変わるときは「new task」で開始する。そうしないとモードはメッセージを次のステップとして扱う。

## 離れる前に

- エージェントが尋ねるのを止めるために「im going to bed」または「im stepping away」と言う。
- 各イテレーションが実行できるチェックとして「完了」を書き、`/loop` にその述語を与える。
- 名前付きベースから新しい worktree を求める。
- エージェントが停止するであろうことを事前に答える（例: 「コミット前に聞かないで」）。
- 後で監査できるよう決定ログを求める。
- 出口を与える: 「数時間後に本当に行き詰まった場合は、停止して理由を書き上げる」。

## 1行でステアリングする

- ゴールを言い直す: 「ゴールは再現だと言った。まだ修正は求めていない。」
- 原則を名指しする: 「apply prove it works. ビルドログではなく実際の出力を見せて。」
- エージェントは既にルールを読んでいるので、原則名が機能する。その返信はルールが変えた決定を名指しする。
