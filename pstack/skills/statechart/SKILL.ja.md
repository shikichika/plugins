# Statechart

このチャートは、読み手の言葉でシステムがどのように状態間を遷移するかを示す。その読み手こそが、挙動が正しいかどうかを判断する。

## 実行

リポジトリの外のスクラッチフォルダで作業する。TLA+ の仕様とその config を記述する。次のコマンドを実行する。

```sh
<skill dir>/scripts/statechart SPEC.tla [--config FILE] [--view FILE] [--out DIR]
```

`scripts/statechart.ts` は TypeScript なので、TypeScript を実行できるランタイムで動かす。

初回実行時には mise で TLC と Java をインストールするため、ネットワーク接続が必要である。

## 仕様の記述

- 読み手が同意する各ルールを INVARIANT として記述する。ルールは画面、結果、保存値、メッセージなどに関するものでよい。モデルにそのルール用の変数がない場合は、変数を追加する。ルールが成立するように弱めてはならない。
- `Next` はアクションの選言として書く。例えば `YouPressPlay \/ YouPressStop`。そうしないと、TLC はすべてのステップを `Next` と名付ける。
- 遷移先のない状態は、それが正しい終端状態であっても `NoDeadlock` を破る。既に INVARIANT や PROPERTY にその名前がある場合、ルールは `CHECK_DEADLOCK` となる。`Next` に、終端状態でのみ真となり何も変更しないアクションを追加する。例えば `Done == phase \in {"paid", "failed"} /\ UNCHANGED vars` のようにし、`step()` でラベルを付ける。

## チャートの選択

判断を要する仕事はあなたが行う。各状態と矢印の文言、フェーズとその色、タイトル、読み手へのレポートである。あなたの仕事はビューモジュールにまとめ、`--view` で渡す。

読み手の言葉を示すために、ビューは `state(vars)` をエクスポートする。`state()` が返す値によって形式が決まる。

- 文字列はフラットなチャートになる: `export const state = (v) => (v.paid ? "Paid" : "Paying");`
- 配列は親子関係のある状態になる: `export const state = (v) => v.main.split(".");`
- オブジェクトはキーごとに並列リージョンを 1 つずつ作る: `export const state = (v) => ({ Playback: v.playback, Volume: v.volume });`

各状態には、読み手が見るものや気にすることをラベル付けする。例えば "Paying" や "Lease held, write pending" のようにする。ラベルに変数名を含めない。`vars` において、TLA+ シーケンスは 1 からのキーを持つオブジェクトなので、`v.pc[1]` は `pc[1]` に相当する。集合は配列である。

ビューは `step(action, from, to)` もエクスポートできる。これは TLC のアクション名と、ステップ前後の値を受け取り、矢印のラベルを返す。各ステップのラベルは、ユーザーに見える通りに書く。例えば "you press play" や "the connect fails" のようにする。コードや TLA+ のアクション名を書いてはならない。チャート上で同じ終端になる 2 つのアクションは同じラベルになり、1 つの矢印を共有する。

ステップが特定の条件下でのみ発生する場合、ラベルの末尾に括弧で条件を読み手の言葉で書く。例えば `you press play [while the file loads]` のようにする。リージョンチャートでは、コマンドが他のリージョンに関する条件をそれらのラベルの言葉で矢印に書き込む。例えば `[when Offline]` のようになる。あなたが括弧書きで書けばそれを置き換えることになり、1 つの状態から出る 2 つの矢印が同じに見える可能性がある。そのため、リージョンチャートでは、他のリージョンに関する条件には括弧を書かない。どのラベルにも現れない値がステップの行き先を決める場合、ラベルで結果を示す。例えば "the roster read fails" のように。

ビューは以下もエクスポートできる。

- `group(vars)` はフェーズ名を返す。各チャート状態はそのグループの色になる。1 つのチャート状態の背後にあるモデル状態が異なるグループに属する場合、その状態は無着色になる。
- `colors` は各グループ名に色クラスを割り当てる。
- `title` はチャート上部に表示される文字列である。

コマンドは各モデル状態ごとに `state()` と `group()` を高々 1 回、各ステップごとに `step()` を高々 1 回呼び出す。チャートとレポートの両方がその結果を使用する。したがって、各関数は引数のみに依存するように作ること。

チャートは、同じラベル内に留まるステップは描画しない。読み手がそのようなステップを見る必要がある場合はラベルを分割する。

矢印はおよそ 20 本以下に抑える。これより多いと読みにくくなる。まず `state()` から粗いラベルを返す。同じ振る舞いをする値には 1 つのラベルを与え、読み手に不要な詳細は省く。例えば、戻り値で何も変わらない実行中の呼び出しなどである。バグ経路の各状態と各マークは残すこと。マージによって `breaks` 状態が `mayBreak` に変わると、ルールがどこで破れるかが隠れる。異なるルールを破る 2 つの状態をマージしてはならない。マージすると読み手はどのルールがどこで破れるかを見られなくなる。それでもチャートが混雑しすぎる場合は、読み手に不要なステップについては `step()` から `null` を返す。例えば、すべての状態にあるリセットや、他の矢印が示す内容を繰り返す矢印のステップなどである。ステップを隠す際は以下のルールに従う。

- 各チャート状態は、開始状態から矢印でたどれる状態に保つ。
- モデルで遷移先を持つ各チャート状態に対して、少なくとも 1 つの出ていく矢印を残す。
- 1 つの矢印に関するすべてのステップを隠すか、あるいは 1 つも隠さない。一部だけ隠すと、その条件が狭まってしまう。
- 引き継ぎの際に、チャートがどのステップを隠しているかを伝える。

## レポートの読み方

- チャートでは、ルールを破る状態は `breaks` クラスを持つ。背後のモデル状態の一部だけがルールを破る場合は `mayBreak` クラスを持つ。Legend には各マークのルール名が示される。2 つのルールが破れる場合は、1 つのマークに両方を記載するので、どの状態がどのルールを破るかを引き継ぎで述べる。リージョンチャートでは、ある状態を含むリージョン状態のすべての組み合わせがルールを破り得る場合、その状態にマークが付く。組み合わせがルールを破り得るのにどの状態にもマークが付いていない場合、その組み合わせに含まれる各状態にマークが付く。
- TLC はルールを破る状態の先にも進むので、チャートはバグの後の状態も表示する。
- TLC がバグの先に進むため、状態数に制限のないモデルは無限に実行され続ける可能性がある。定数を小さく保つか、CONSTRAINT を追加する。
- VIEW または SYMMETRY を使うと、TLC は同一視する複数の状態を 1 つとして数え、チャートもその 1 つの状態を描画する。矢印はステップが到達する状態ではなく、こちらに向かう可能性があり、レポートはその旨を示す。
- TLC は CONSTRAINT や ACTION_CONSTRAINT の先の各状態でもルールを検査するが、その状態を探索せず、デッドロックの検査も行わない。TLC のルールに対する最短経路がそのような状態で終わる場合、チャートはその状態を描画し、レポートはその経路を示す。チャートは境界の先の他の状態は描画しない。そのような状態でのデッドロックは表示されない。TLC は ACTION_CONSTRAINT が除外する各ステップ後のルールも検査する。これは別経路で次の状態に到達した場合も同様である。TLC のルールに対する最短経路がそのようなステップで終わる場合、チャートはそのステップを描画する。
- コマンドは記述された config に基づき 1 ワーカーで TLC を用いてルールを検査する。ルールが破れた場合、コマンドはそのルールを除いて再度 TLC を実行し、破れるルールがなくなるまで繰り返す。最初の破綻後、各実行は 10 万の異なる状態で停止し、大規模なモデルが無限に実行されないようにする。実行が境界に達するかエラーで停止した場合、レポートは検査できなかったルールを "Rules not checked" として列挙し、チャートはそれらをマークしない。検査されないルールは成立する場合も破れる場合もある。検査するには、破れるルールを config から削除するか、モデルを小さくする。境界は TLC の変数順序を変更するモジュールを追加するため、プロパティに対しては境界なしの実行とは異なる反例が見つかる可能性がある。
- `tlc.out` は記述された config に対して TLC が出力したものである。チャートが破れたルールのバグ経路を示さない場合、`tlc-RULE.out` はそれを見つけた実行で TLC が出力したものである。TLC は最初の警告を繰り返し出力するが、素の TLC はそれを 2 回表示する一方、`tlc.out` では 1 回しか表示されない。これは TLC がこのコマンドが読む出力から 2 つ目のコピーを除外するためである。これは Java が `-XX:+UseParallelGC` で実行されるときにのみ起こる。そうでなければ TLC の最初の警告は、そのフラグを渡すことを勧める助言であり、1 回だけ出力される。

## チャートの表示

`chart.mmd` を `mermaid` コードブロックとしてユーザーに表示する。チャートには、記述された config に対して TLC が数える状態数の 500 という予算がある。それを超えると、チャートは破れたルールへの経路のみを描画し、破れたルールがない場合は `chart.mmd` を書き出さない。それでも各ルールは検査され、レポートは状態数と各バグ経路を示す。グラフ全体を見るには、モデルを小さくする。

Pele でチャートを描画する。ユーザーが画像を要求した場合や、チャートがテキストとして読むには大きすぎる場合は、`references/render.md` に従う。ユーザーが要求しない限り、別のレンダラーを使ってはならない。

## 引き継ぎ

各チャートとその Mermaid テキストを、判断を下すべき人物に渡す。各バグについて 1 行ずつ、ルール、そのルールに対する読み手の文、レポートに付された経路の番号を添える。モデルが省いた要素も述べる。新しい `--out` フォルダでファイルを再生成するコマンドを示す。

モデルがコードを記述している場合、各バグ経路を実際のコードに対して、テストまたはライブリプロとして、アクションごとに 1 ステップずつ再現する。バグが発生しない場合は、発生しないことを示すまで、モデルの方が誤っていると考える。
