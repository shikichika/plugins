# Automate me

ユーザーの作業上の慣習を、エージェントが従うスキルに変換するためのガイド付きフロー。出力は、ユーザー向けにカスタマイズされた 1 つの `-mode` スキル（例： `jay-mode`、`priya-mode`）。

このスキルは他の 3 つを調整する：インラインのマイニングパス（ステップ 1 を参照）、Cursor 組み込みの `create-skill`（執筆）、**unslop** スキル（散文の規律）。これらをシーケンス化する。置き換えるわけではない。

## Flow

### 0. 既存のスキルを確認する

ユーザーのハンドルに一致する `.cursor/skills/**/*-mode/SKILL.md` と `~/.cursor/skills/*-mode/SKILL.md` を再帰的に探す。モードスキルは、最上位だけでなく、個人カテゴリディレクトリ（`.cursor/skills/<handle>/`）にも存在できる。存在する場合は、`AskQuestion` で意図を確認する（ユーザーがすでに「スキルを更新して」などと言っている場合を除く）：

- 既存のスキルを更新する（繰り返し実行のデフォルト）
- ゼロから始める（稀。実行前に理由を尋ねる）

更新モードでは、残りのフローが変わる：
- ステップ 1 では、スキルが最後に編集されて以降の履歴のみマイニングする（`git log -1 --format=%cI <path>`）。
- ステップ 2 では、何がゼロから捉えるべきかではなく、何が変わったか、または欠けているかを尋ねる。
- ステップ 4 では、既存のファイルをその場で編集する。ユーザーが矛盾していないセクションは保持する。新しい証拠があるものは改訂する。本当に新しいルールのためだけに新しいセクションを追加する。

### 1. 履歴をマイニングする

分散する前に、アクティブなワークスペースのトランスクリプトを特定する。システムプロンプトはワークスペースの `agent-transcripts/` ディレクトリを示す。そのパスのみを使用する。`~/.cursor/projects/*/` 全体を glob しない。これはワークスペースの境界を越え、無関係なプロジェクトのプライベートチャットを読んでしまう。

そのスコープ内の最近のエージェント会話を調査し、繰り返されるパターンを探す。履歴のスライス全体で複数の並列サブエージェントを実行する（例：直近 2〜4 週間を 3 スライスに分割し、各スライスに十分な材料があるようにする）。各サブエージェントの推論レベルはそのジョブに合わせて選び、**poteto-mode** スキルの Subagents セクションに従う。各スライスマイニングサブエージェントは、親が提供するワークスペーススコープのパスからトランスクリプトを読み、以下のシグナルを探し、見たパターンの短い構造化リストと証拠へのポインタを返す。デフォルトで狩るべきシグナル：

- 応答の好み（長さ、トーン、形式、「もっと分かりやすく」の修正）
- 委任の習慣（サブエージェント、モデル、特化ワークフロー、並列性）
- 検証の姿勢（「完了」の意味、ユニットテスト vs ライブ再現、レビュアー）
- コードと散文の規律（スタイル、引用される原則、lint/format ツール）
- プロセスの慣習（worktree、コミット、PR、レビュー/マージツール）
- メタ的な好み（タスク中のスキル修正、新しいスキルの提案）

シグナルを格上げする前に、スライス間でクロスチェックする。2 つ以上のスライスで観察されたパターンは高信頼度。単発のシグナルは弱く、通常は破棄される。

### 2. ユーザーに直接尋ねる

マイニングは、まだ表面化していない意図を見逃す。ユーザーにゼロから入力させるのではなく、`AskQuestion` ツール（構造化多肢選択）を使う。

形状：各質問に 4〜6 のオプションがある 1〜2 の質問。カテゴリ質問には `allow_multiple: true`。広く始め（「どの領域が最も重要ですか？」）、選択された領域について具体的なオプションで追跡する。構造化ラウンドの後、1 つの自由形式のチャット質問で、オプションが見落としたものを捉える。

20 の質問をダンプしない。

### 3. 発見をクラスタ化する

結合したシグナルをセクションにグループ化する。一般的なもの（当てはまるものだけ使う）：

- **応答スタイル**：長さ、トーン、形式。
- **自律性**：確認せずにどれくらい行うか、MCP ツールの使用。
- **まず理解する**：変更をスコープする、または調査する際に手を伸ばすスキル。
- **サブエージェント**：デフォルト、並列性、モデルからタスクへ、特化ワークフロー。
- **散文/コードの規律**：原則、lint ツール、スタイルガイド。
- **レビューと検証**：再現姿勢、検証スキル、ライブテストツール。
- **プロセス**：git worktree、コミット、PR、レビュー/マージツール。
- **スキル**：スキル執筆の習慣、fix-the-skill-first、新しいスキルの提案。

**poteto-mode** スキルは形を示す。粒度のために読む。その内容をコピーしない。ユーザーのルールは poteto-mode のルールと同じではない。

### 4. スキルを下書きする

Cursor 組み込みの `create-skill` スキルを使ってスキルを作成する。配置：

- パス：既存のモードスキルのカテゴリを保持する。新しいモードの場合、リポジトリにそのハンドル用の確立された個人カテゴリがある場合は `.cursor/skills/<handle>/<handle>-mode/SKILL.md` を使う。それ以外の場合は、プロジェクト内の `.cursor/skills/<handle>-mode/SKILL.md` をデフォルトにする（またはユーザーが個人スキルを好む場合は `~/.cursor/skills/<handle>-mode/`）。
- ハンドル：ユーザーの名または選ばれた識別子。
- Frontmatter の `description`：「コードを書く」や「PR をレビューする」のような一般的なキーワードではなく、名前 + `/<handle>-mode` + 「彼らのスタイルで作業する」でトリガーする。
- Frontmatter のフォーマット：`create-skill` の YAML ルールに従う。`description` は 1 つの YAML スカラーとして保つ。句読点やラッピングが必要な場合は、引用符で囲むか、インデントされた継続行を持つ `description: >-` を使う。
- Frontmatter の `disable-model-invocation: true` をデフォルトにする。ユーザーがモードを毎ターン適用したいと明示的に望む場合のみオプトアウトする。

### 5. 散文を反復する

**unslop** スキルと `create-skill` の執筆ガイドラインを各行に適用する。

下書きをユーザーに見せ、フィードバックを得る。複数の反復を予想する。容赦なく削る。モードスキルはマニュアルではない。

### 6. ランディング

main からの worktree で作業する。コミットして PR を開く。main に直接プッシュしない。

## Guardrails

- **1 つの会話に過学習しない。** 1 回述べられ、別の時に矛盾された好みはノイズである。コード化する前に複数のインスタンスを要求する。
- **賢ぶらない。** 他のスキルの内容を言い直したり、メタファーを発明したり、エージェントの読者のために「詩的」な散文を書くのは、利益のないコストである。運用的に保つ。
- **参照し、インライン化しない。** ユーザーが頼っている他のスキルは、貼り付けた抜粋ではなく、パス参照として表示する。他のところで維持している原則ドキュメントについても同じ。
- **セクションを最小限に保つ。** ユーザーがそこに特定の非デフォルトルールを持っている場合のみセクションを追加する。「明確にコミュニケートする」はセクションではない。「短い段落。オプションを比較する際はテーブル。項目が本当に並列である場合のみ箇条書き。」はセクションである。
- **命名規則を汎用的に。** 命令形では著者の名ではなく「ユーザー」または「人間」を使う。
- **対称性を強制しない。** ユーザーが書き留めるに値するプロセスルールを持っていない場合は、プロセスセクションを完全にスキップする。

## Evaluation

`-mode` スキルは主観的な出力である。`create-skill` 形式のテスト/反復ベンチマークループはここでは有用ではない。ユーザーとのバイブチェック：彼らのように読めるか？何か見逃したか？そして出荷する。

スキルのトリガー精度が実際に問題になった場合のみ、description 最適化ループを実行する。

## When not to use

- ユーザーがタスク固有のスキルを望む（作業の慣習ではない）：`create-skill` のみ、マイニング不要。
- ユーザーが 1 つの狭いワークフローを捉えたい（例：「コミットメッセージの書き方」）。それは通常のスキルであり、モードスキルではない。
