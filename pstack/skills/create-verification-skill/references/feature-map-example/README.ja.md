# Notes 検証マップ

このディレクトリは、Notes のユーザー向け挙動を検証するための維持されたソースである。アプリを駆動する前にインデックスを読み、次に一致する機能ファイルをレシピとして使う。

## ベースライン前提条件

- 使い捨てのデータディレクトリで `http://127.0.0.1:4173` に Notes を起動する。
- 並行実行が状態を共有しないように `NOTES_DATA_DIR=/tmp/notes-verify-$RUN_ID` を設定する。
- タイトル `Quarterly plan` と `Grocery list` のノートをシードする。
- `control-notes` と `notes` CLI を `PATH` に置く。
- `control-notes doctor` を実行し、期待される URL、データディレクトリ、ビルドリビジョンを要求する。
- この検証実行で開始されなかったインスタンスを決して駆動しない。

## 駆動の慣習

- 前提条件に別途記載がない限り、すべてのレシピはベースライン状態から始める。
- CSS セレクタや DOM の位置ではなく、ARIA ロールとアクセシブル名を優先する。
- すべてのコマンドを文字通りに扱う。引用符で囲まれた名前とフラグは変更しない。
- ブラウザアクションは `control-notes browser` を通して実行する。
- ターミナルアクションは `control-notes cli -- <command>` を通して実行する。
- 変更の後はシードデータを復元する。クリーンアップ中に証明アーティファクトを削除しない。

## 証明とスキップの報告

- 最終画面だけでなく、ユーザーアクションと結果の状態を捉える。
- UI の証明には、ARIA スナップショットと、アプリの識別情報が見えるスクリーンショットを含む。
- CLI の証明には、コマンド、stdout、stderr、終了コードを含む。
- 変更の証明には、保存された値の読み取り専用の 2 つ目のビューを含む。
- 各アーティファクトとともに、使用した機能 ID とエントリポイントを記録する。
- 到達できないパスは、試みたコマンドと満たされなかった前提条件とともに報告する。
- スキップされたエントリポイントを、別のパスを通して検証されたと報告しない。

## 機能エントリ契約

各機能ファイルは H1 タイトルと、ユーザーに見える挙動を記述する 1 段落で始まる。次に、以下の順序で正確に 4 つの H2 セクションを使う。

1. `Sub-features` は、各挙動について 1 行の短い ID をリストする。
2. `How to get to it (user POV)` はすべてのユーザーエントリポイントをリストする。
3. `Driving it with <harness>` は `Preconditions:` で始まり、ラベル付き箇条書きで各ユーザーアクションを正確なコマンドと観察可能な結果とペアにする。
4. `Gotchas` は、検証実行を無駄にしたり無効にしたりし得る罠をリストする。

実装の詳細はマップに含めない。ユーザーパス、安定したハンドル、必要な状態、コマンド、観察可能な証明のみを名指しする。

## 機能

- [Create a note](./create-note.md) は、ブラウザと CLI の作成、キャンセル、永続化、クリーンアップをカバーする。
- [Search notes](./search.md) は、マッチング、空、クリア状態を含むツールバー、キーボード、CLI 検索をカバーする。
