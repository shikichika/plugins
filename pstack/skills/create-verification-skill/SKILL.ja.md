# Create a verification skill

真剣なプロジェクトには、実アプリを駆動し挙動を証明するスクリプト化された方法が必要である：起動し、ユーザーが行うように機能を演習し、証拠を捉える。このスキルは、それをリポジトリに合わせたプロジェクトローカルスキル（`.cursor/skills/verify-<app>/`）として生成する。ジェネレータの出力は、人間向けではなく、アプリを見たことがないエージェントが、タスクの最中に初めて読むために書く。

## 1. ユーザーではなく、リポジトリにインタビューする

以下をコードベースから答え、観察できないことだけをユーザーに尋ねる：

- **サーフェス：** ユーザーが実際に触れるのは何か？ Web UI、CLI/TUI、デスクトップアプリ、API、モバイルアプリ、ライブラリ？リポジトリにはいくつか存在し得る。主要なものを選び、残りを記す。
- **実行：** アプリはローカルでどのように起動するか？リポジトリ自身の文書化された dev コマンド（package scripts、Makefile、README quickstart）を優先する。ポート、環境変数、シードデータ、認証を記す。
- **駆動：** エージェントはどのようにプログラマティックに対話できるか？まず既存のハーネス - Playwright/Cypress spec、expect スクリプト、PTY ヘルパー、curl 可能なエンドポイント、デバッグポート。次にのみ一般的なレシピを選ぶ：Web と Electron 向けの browser/CDP、CLI/TUI 向けの tmux/PTY ハーネス、サービス向けのプレーン HTTP。
- **観察：** どんな証拠を捉えられるか？スクリーンショット、ターミナルトランスクリプト、レスポンスボディ、ログ、終了コード、DB 状態。
- **分離：** 2 つのインスタンスを並行実行できるか（ポート、データディレクトリ、プロファイル）？できない場合は、生成されたスキルでその旨を明示する：共有インスタンスを二重駆動することを拒否する方が、ユーザーのセッションを破損させるよりはよい。

チェックアウトがそのままビルドまたは起動しない場合、生成前にそれを修正する（または正確に報告する）；壊れた基盤に対して書かれたスキルは、間違った手順を教える。無関係な欠落アセット（API が決して提供しない静的ディレクトリ、サンプル設定）が起動をブロックする場合、生成されたスキルはそれを作成でき、検証用足場として明確にマークし、クリーンアップで削除する。

## 2. スキルを生成する

YAML frontmatter（`name: verify-<app>` と、アプリ、サーフェス、いつ手を伸ばすかを名指しする `description` - frontmatter なしではスキルは登録されない）を持つ `.cursor/skills/verify-<app>/SKILL.md` を書き、以下のセクションそれぞれをインタビューで実際に見つかったものに基づいて（プレースホルダは残さない）：

- **Launch：** 検証のためにアプリを起動する正確なコマンドと、準備ができたとわかる方法（ログ行、プロンプト）。Launch は、マイグレーションとシードデータを含め、空のデータディレクトリから使用可能な状態に到達しなければならない。Ready とは、プロセスが応答するだけでなく、使用可能であることを意味する。データベースのヘルスチェックは、その初期化スクリプトがまだ実行中でもパスする可能性がある。teardown を含める。短命の CLI や TUI には維持するサーバーがない：launch は、バイナリをビルド（または deps をインストール）することを一度意味し、その後、各 drive を独自の分離された PTY または tmux セッションで開始する。
- **Doctor：** 「このインスタンスは駆動する価値があるか？」に答える、1 つの読み取り専用チェック - プロセスが起動している、正しいバージョン/ビルド、ポートが自分のもの、認証が有効。何かおかしく見えるときはいつでも、エージェントは最初にこれを実行する。
- **Drive：** 例ではなく、このリポジトリからの実セレクタ/コマンドを持つハーネスレシピ。座標とタブ順ではなく、安定したハンドル（ARIA ラベル、data 属性、プロンプト文字列、ルートパス）を優先する。
- **Evidence：** 証拠として何を捉え、どこに置くか。証明基準を明示する：内部セッターやテスト専用エンドポイントではなく、実ユーザーパスを演習する；最終画面だけでなく、アクションと結果の状態を捉える；可視なものに加えて副作用（書かれたファイル、挿入された行、送信されたメッセージ）を検証する；本番境界がすでに外部システムを分離している場合のみモック。安全パスがドライランやテストモードの場合、名前を信頼するのではなく、観察（ファイル、ネットワーク、git ref）によって実際に何をスキップするかを検証する：一部のドライランはネットワークに触れたりブラウザを開いたりする。
- **Cleanup：** 実行が作成したインスタンスをどう tear down するか。プロセス名で kill しない；自分が起動したものを kill する。Cleanup はインスタンスとスクラッチ状態を削除するが、証拠は決して削除しない：証明アーティファクトは teardown を生き延び、スキルが名指しする場所に残る。
- **Helpers：** スキルが出荷するスクリプトは実行可能であり、その呼び出し方法はスキル本文に示される。読者がリバースエンジニアリングしなければならないヘルパーはヘルパーではない。

## 3. feature map をシードする

`.cursor/skills/verify-<app>/features/README.md` と、識別できる各ユーザー向け機能ごとに 1 ファイルを作成する（まずは上位 3〜5 を目指す。ルート、コマンド、メニュー、ドキュメントから）。[`references/feature-map-example/`](references/feature-map-example/) の形に従う。README インデックスと機能ごとに 1 ファイル。各ファイルは、ユーザー視点から次に答える：機能とは何か、どう到達するか、ハーネスでどう駆動するか、観察可能な終了状態が機能することを証明する。4 つの H2 は `Sub-features`、`How to get to it (user POV)`、`Driving it with <harness>`、`Gotchas`。シードデータに journey が必要な前提条件が欠けている場合、journey は失敗を報告し、理由はその機能の `Gotchas` に行く。パスさせるために journey を弱めない。map はリポジトリの維持される検証ソースである；1 つの便利なエントリポイントを駆動する証明は、map が他をリストする場合は不完全である。

## 4. 引き渡す前に生成されたスキルを証明する

その指示をエンドツーエンドに一度実行する：launch、doctor、マップされた 1 つの機能を駆動（1 つで十分；map は後の実行が残りをカバーできるように存在する）、証拠を捉え、クリーンアップ。クリーンアップ後、証拠が名指しされた場所にまだ存在することを確認する - 証明を食うクリーンアップはこのステップに失敗する。失敗したものを修正し、失敗した反復の後にも生成されたクリーンアップを実行する。そうすることで、壊れた試みがプロセスとポートを取り残すことはない。実行されなかった生成スキルは下書きであり、成果物ではない。実対象の代わり（新鮮な VM の代わりにコンテナ、リモートスタックの代わりにローカルスタック）で証明した場合は、代わりが行ったセットアップステップで、実対象が行わないものをすべてリストする。それらのステップは、実対象での実行がカバーするまで未検証のままである。

## 5. メンテナンスループを提供する

アプリが変化してもマップを正直に保つために、ユーザーを `/maintain-verification-skill` に導く。頼まれた場合のみ頻度を提案する。
